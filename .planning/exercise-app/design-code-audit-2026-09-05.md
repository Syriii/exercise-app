# 设计与代码重新审查（2026-09-05）

> 后续状态：本报告是本日审查时点的证据。随后产品所有者已完成相关业务讨论，结论汇入正式产品、领域和体验文档；下文的建议／待讨论措辞保留历史含义。C1–C5 尚未修复，测试记录也不是新设计验收。当前工作以 task_plan 为准。

本轮是审查结果，不是新的产品定稿或实施授权。依据产品所有者最新表述：讨论完整体设计后输出文档，再进入改造。保留已确认的五页职责、训练计划与实际记录分离、统一食物选择、身体数据归“我的”等方向；以下建议尚未自动替换这些确认结论。

## 结论

当前页面方向合理，但“业务逻辑已经完整、只剩界面改造”的判断过早。存在尚未定义清楚的正常使用路径、真实代码缺陷，以及新设计需要后端和数据结构支持的能力。现有架构与大量领域能力可以复用，没有发现需要更换 Vue 或重建整套服务端的理由。

## 一、现有代码缺陷

### C1 / P1：保存一个动作会覆盖其他动作未保存的输入

- 场景：先填写 A、B 两个动作，点击保存 A。
- `apps/web/src/views/TrainingPage.vue:241` 的 `syncActualForms` 无条件重建全部动作表单；`:259` 的 `applySession` 在任何单项保存成功后调用它；`:607` 起的 `saveItem` 使用这条路径。
- 结果：B 的未保存次数、重量、备注被服务端旧值或空表单覆盖。这直接妨碍用户运动后集中填写。
- 验证：读取实际源码，提取两个函数，经 TypeScript 转译后在隔离 VM 执行。B 原本为 12 次、60 kg、备注 unsaved，保存 A 对应的服务端响应后 B 全部变空。此为函数级复现，未进行浏览器点击复现。
- 修正方向：编辑草稿与服务端事实分开；局部保存只更新目标项。未来整次训练保存应一次提交实际内容，失败保留整份草稿。

### C2 / P1：补记旧体重可能被当作最新体重

- `apps/web/src/views/SettingsPage.vue:263` 创建测量时，不论用户选择哪个日期，`measuredAt` 都填写当前时间；修改时又强制换成所选日期中午。
- `apps/server/src/modules/planning/postgres-repository.ts:132` 的列表和 `:136` 的最新值查询都按 `measuredAt` 倒序排列。
- 场景：9 月 5 日先记录当天 70 kg，再补记 9 月 1 日的 72 kg。
- 验证：按前端实际请求结构调用内存 PlanningService/仓储；最新值变成 9 月 1 日的 72 kg。真实 PostgreSQL 仓储具有相同排序规则，但本轮未连接数据库复现。
- 影响：当前体重及依赖它的新参考可能使用旧数据；只修改备注也可能改变同日测量顺序。
- 修正方向：实际测量时间与录入时间分开；补记使用实际日期/时间，普通修改保留原测量时间；当前值按有效测量事实选择。

### C3 / P1：图片任务入队失败后，留下无图片的等待任务

- `apps/server/src/modules/image-analysis/service.ts:30` 先保存媒体和分析记录，`:31` 再入队；失败时 `:33` 删除图片，但没有回滚或修正已保存记录。
- PostgreSQL `create` 内部事务在入队前已经结束，见 `apps/server/src/modules/image-analysis/postgres-repository.ts:15`。
- 验证：在内存依赖中注入 enqueue 异常，得到 `status=pending`、`imageAvailable=true`、实际图片字节不存在、活跃任务数为 1。
- 影响：页面显示等待，用户无法按失败任务重试；此类记录还占据账号分析容量。
- 修正方向：采用可恢复的事务投递或补偿流程，使业务任务状态、媒体状态和队列投递保持一致。

### C4 / P1：图片执行中断后，重复投递不能恢复 running 状态

- `apps/server/src/modules/image-analysis/postgres-repository.ts:27` 只允许 pending 状态开始；`service.ts:40` 遇到 not_ready 直接返回；队列定义的 retryLimit 为 0。
- 场景：Worker 已写 running，但在成功或失败写回前退出。即使再次投递相同任务，业务层也拒绝接手。
- 验证：内存仓储执行 beginAttempt 模拟中断点，再调用 process，结果仍为 running，尝试数仍为 1。
- `apps/server/src/entrypoints/worker.ts` 的恢复调用针对 portability，未发现针对图片 running 状态的恢复扫描。临时媒体过期清理也只更新媒体，不恢复该分析任务。
- 修正方向：为过期执行建立有边界的接管/失败规则，允许有效重试并排除旧 Worker 的迟到写回。队列通用故障测试不能替代业务状态恢复测试。

### C5 / P2：常用食物修改份量时，营养不会跟着变化

- `apps/web/src/views/NutritionPage.vue:367` 把份量和营养分别带进表单，`:355` 保存时分别原样提交；服务端 `nutrition/service.ts:143` 也不做按基准换算。
- 验证：创建 200 g / 232 kcal 的米饭贡献，沿前端路径只把份量改为 100 g，保存结果仍为 232 kcal。
- 当前公开包装食品的“按克数带入”有独立换算函数，但不能覆盖普通条目的后续份量编辑。
- 修正方向：食物营养基准、当次食用量和换算结果分开；统一所有来源的份量换算。自由填写营养总值可保留为按需纠错，不充当普通份量编辑的默认行为。

## 二、设计需要补齐的业务规则

### D1：照片识别必须接到可复用的单个食物

这是最重要的设计与代码断点。用户希望昨日包子、鸡蛋、豆浆中的鸡蛋和豆浆能复用于今天。

- `image-analysis/types.ts:4` 的候选只给每个可见食物名称、文本份量与备注，营养值只在整餐层。
- `nutrition/service.ts:112` 和 PostgreSQL 图片成功写回均创建一条 whole_meal 贡献。
- `db/schema/index.ts:905` 的 sourceAnalysisId 唯一约束还限制一次分析只能关联一条贡献。
- 因而当前“识别出鸡蛋”不等于已经存在可独立修改、移除、复用的鸡蛋食物记录。

建议：可分辨的菜品/食物形成独立条目，份量和营养可单项修改；真正无法拆分的混合菜可以作为一道食物，不强行拆成原料。整餐汇总由条目计算；修正某项不能同时保留覆盖同一内容的整餐总量。这需要供应商契约、结果保存及相关约束一起调整。

### D2：统一食物库还需要明确身份、单位与没有结果时的出口

- 当前 `nutrition/service.ts:193` 搜索的是个人模板和最近 90 天餐食，按“名称、份量、营养值”等全字段去重，最多返回 50 项。
- 同一种米饭 100 g 和 200 g 会成为不同候选；没有统一食物 ID、分类目录、用量单位映射和全库分页。
- 建议：同一食物身份下保存多个可选份量；常用与近期影响同一列表排序。全量可浏览通过分页承接，不等于一次加载整库。
- “个、碗、杯”只有在有明确换算基准时才能换算；没有基准时允许补充份量或建立个人条目，不能凭单位名猜重量。
- 普通/包装食品统一入口，同时保留能区分具体食物的熟/生、品牌、做法等属性。
- 搜不到、分类为空、外部来源不可用时，要有保留选择并补充个人食物的出口。
- 原始“把鸡蛋设为常用”的主动意图，不应悄悄收窄成仅靠算法判断；建议在同一列表上保留轻量常用标记，是否采用随文档整体讨论，不重新增加常用分区。

### D3：训练改成事后记录，还需要降低填写成本

- 已确认“计划 + 记录”正确，但当前草案仍可能要求运动后填写大量逐组明细。
- 建议默认支持动作级批量填写，例如“卧推：3 组 × 10 次，40 kg”；组间不同再展开修改。跑步按距离/时长填写。
- 不清楚重量或精确时间时仍可保存明确知道的事实，不从计划目标量静默制造实际量。
- 草稿应支持整次保存、失败保留、离开后合理恢复；草稿不是“正在训练”，不应恢复旧训练状态机。
- 目前服务端入口仍为 startSession → 单项更新 → finishSession；没有直接提交某日期整份实际训练记录的完整接口。

### D4：计划进度不能简单等于记录过几个动作

- 场景：计划卧推 4 组，实际 2 组；同日分两条记录；上午记录后又修改今天计划；存在完全独立的训练记录。
- “完成多少、剩余多少”需要明确比较单位和计划快照，而不是仅凭有一个同名动作就算完成。
- 建议记录保留计划关联并根据对应实际量汇总，独立记录不自动匹配；多条记录不可重复计算。首页保留用户要求的简短摘要，详细差异归训练页。
- 当前日程主要引用来源模板/训练单元，`training/service.ts:652` 在开始训练时才读取来源并形成快照；这与草案“安排到日期时建立当天独立快照”不同。
- 应区分修改可复用计划和只调整当天安排，已有记录继续保留原计划上下文。

### D5：简化图片状态与保留可理解的反馈需要同时完成

- 保留已确认的自动计入和直接修正体验，不重新引入“暂定/采用值”工作流。
- 页面仍需表达上传中、识别中、识别失败，以及相关营养暂缺。否则数字为 0 时用户无法分辨“没有吃”还是“尚未算出”。
- 自动计入是现有确认方向，不应在新文档里又写成必须确认后才保存。
- 用户离开页面后继续识别、重新进入能找到结果；手动修改后迟到结果不覆盖；同餐追加照片不重复计入同一食物。
- 原图删除应绑定实际产品事件或保留期。既然不再要求专门确认，不能继续依赖已被删掉的“确认采用”按钮完成整个生命周期。
- 当前未发现账号级自动识别开关或“关闭自动但可手动识别”的完整代码路径；上传接口直接入队。旧文档写有这项能力，但它仍需实现。

### D6：我的、历史和首次设置需要共享数据入口与状态

- 保留已确认的“我的 → 身体数据”稳定入口，历史身体摘要跳转到同一记录；身体趋势可复用同一详情，避免做两套完整管理页。
- “记录新测量”与“修改过去错误”分开，避免覆盖测量时间序列。
- 目前身体记录只支持创建/更新，未发现单条删除接口；训练也未发现整次实际记录删除接口。餐食元数据更新接口存在，但当前饮食页未提供调用它的编辑入口。不能在文档中只写“修改删除”便认定已实现。
- 首次设置必须保留；必填的是完成必需步骤，不能把每个扩展字段都设成必填。腰围是否必需应依据已确认字段范围，不从“身体资料必填”推导出所有身体指标强制填写。
- 中途离开后恢复到未完成步骤；已有用户不因换入口再次填表；资料已填但不适用某个计算方法时仍能使用记录功能。
- 当前路由守卫只检查登录、强制改密和管理员权限，没有首次设置完成检查；设置页用档案/策略 revision 均为 0 且测量为空判断首次进入，无法表达部分完成状态。

## 三、工程与文档判断

- 可复用的基础：Vue 页面与 API 分离、PostgreSQL 仓储、乐观版本控制、餐食修订与独立快照、图片异步处理、账号隔离及测试基础。图片成功结果和首次整餐贡献在 PostgreSQL 事务内写回，这一边界值得保留。
- 新设计需要的不只是移动卡片：统一食物身份/营养基准、单项图片结果、整次训练保存、日程快照与进度规则、首次设置完成状态等涉及 API 或数据契约。
- 前端大型页面把查询、草稿、表单同步、保存和结果展示集中维护，已有 C1 这样的交互缺陷。以后按实际任务拆分记录编辑器与数据操作，服务端事实和未保存草稿分别管理；无需为此提前抽取跨应用公共层。
- 当前 task_plan 的“当前阶段”仍指向真实餐食样本复核；正式 product/domain/experience 文档保留旧状态机；核对稿内也混有旧初稿与新确认结论。正式文档输出时应明确旧内容的历史性质，清除已回答问题和过期下一步。
- 用户只确认合并“方案/模板/计划”的概念，不能因此推导出所有周期日期安排都应删除；能力是否保留需依据最新明确表述，仍有争议的删减不自动执行。
- 现有记录、计划和营养来源需要前向兼容。不能为了新界面直接删除旧状态或历史数据。
