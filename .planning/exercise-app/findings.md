# 项目事实、假设与决策

> **状态：规划重置前材料。** 本文件保留历史发现与风险，不再驱动讨论或充当当前产品事实源。

> 本文件只保存规划所依据的信息。事实、假设与决定必须分开，避免把设想误当成需求。

## A. 已确认事实

### 项目意图

- 产品最初服务于项目所有者本人。
- 验证后希望开放给朋友使用，长期希望开源给更多人。
- 长期关注两个问题域：
  - 如何训练，以及实际练了多少；
  - 吃了什么，以及营养结构如何。
- 希望先做网页端，达到满意效果后再转为 Android APK。
- 视觉偏好是运动、简洁、实用。
- 用户明确希望先做规划和讨论，而不是直接产出完整第一版。

### Phase 1 访谈证据

- 项目的直接触发点是看到一款健身 App，并认为其中有值得借鉴的设计。
- 用户明确提出的产品能力包括：
  - 自己制定运动计划和饮食计划；
  - 判断当天是否去健身房，并安排练习动作；
  - 查看动作标准姿势的视频；
  - 根据个人体重估算运动消耗；
  - 给出每日蛋白质、脂肪及另一项尚待确认的营养摄入目标；
  - 拍摄一顿饭，由 AI 估算各项营养摄入。
- 这些能力属于已确认的产品目标；它们的交付顺序尚未确定。
- 参考 App 的名称、实际使用深度、不能直接满足需求的原因尚未说明。
- 用户没有实际使用参考 App，只看过截图；因此目前不存在与该产品的真实使用对比。
- 最能引起用户兴趣的单项能力是“拍照后由 AI 估算一餐的营养”。
- 这提示“降低饮食记录和营养估算成本”可能是首要问题，但目前仍是假设，需要通过现实场景验证。
- 用户目前主要吃食堂餐；菜品缺少明确配方、份量和营养标签，因此很难手动记录。
- 用户目前没有形成可行的记录方式，但明确希望进行饮食记录。
- 当前最有证据支持的问题候选不是单纯记录食堂餐，而是建立“每日营养目标与实际摄入之间的低成本反馈闭环”。
- 照片难以直接判断隐藏用油、调味料和精确配方，因此“快速、可修正、有误差提示的估算”比“精确计算”更符合实际。
- 用户期望的完整流程是：
  1. 根据个人信息与目标计算一天需要的蛋白质、脂肪等营养目标；
  2. 拍摄每顿饭，估算该餐热量和营养成分；
  3. 将每餐估算累计到当天，并与每日目标对照。
- 食堂是拍照估算价值较高的现实环境，但不是产品目标本身。
- 用户明确认为训练与饮食在健身目标上不可分割，但两件事本身应当独立。
- 用户期望的联动原则是：当天训练较多时相应提高饮食摄入目标，训练较少时相应降低。
- 因此当前产品模型是“两个独立模块 + 一层每日目标联动”，而不是把所有能力做成一个不可拆分流程。
- 用户认为饮食是健身过程中难度最大的部分，尤其是在依赖食堂、无法得知配方和份量的情况下。
- 这一表述使饮食目标与拍照估算成为目前证据最强的首要价值；训练仍是独立模块和营养调整的必要输入。
- 训练模块的目标能力已经明确：自定义训练计划、今日训练安排、动作标准视频、实际训练量记录、基于个人信息和训练情况的消耗估算、训练提醒。
- 用户工作日可能通常在晚上训练，但周末、假期或其他安排下也会在白天训练；营养参考需要在训练完成前先依据计划给出暂定值，不能把晚上设为默认时段。
- 如果计划训练没有完成：
  - 当天还会继续进食时，应根据实际活动调整剩余摄入参考；
  - 用户已经结束当天进食时，不能改写已吃内容，应提示当天摄入与最新参考的偏差；
  - 状态未知时只显示参考变化。
- 这证明联动需要同时考虑训练计划、实际完成状态和后续进食状态，而不只是一个静态公式或时钟判断。
- 用户明确要求训练提醒与饮食提醒分开：
  - 训练提醒只处理训练计划、开始和完成状态；
  - 饮食提醒只处理摄入目标、缺口和超标状态；
  - 两个模块共享联动后的数据，但不混淆提醒语义。
- 用户确认个人使用阶段需要同时满足三类成功表现：
  - 可以持续记录饮食；
  - 可以知道当天还应该摄入多少；
  - 可以更稳定地完成训练计划。
- 三类表现分别对应持续使用、饮食决策支持和训练执行，具体验证周期与最低达标线尚未确定。
- 用户确认第一轮个人验证周期为连续 14 天。
- 用户明确反对把使用频率变成产品对用户的强制要求。
- 用户认为使用多少应由用户决定；按照设计，记录越多效果越好，但少用仍应可以正常使用。
- 因此“14 天”是验证观察窗口，不是连续打卡要求；使用频率是观察信号，不是产品内的达标配额。

## B. 尚待验证的产品假设

- 首个 MVP 需要同时包含训练与饮食的最小能力，才能验证跨模块联动。
- 计划训练量还是实际完成训练量应作为营养目标的主要调整依据。
- “指导 + 记录 + 回顾”是最合适的首要闭环。
- 项目所有者的需求能够直接代表朋友或开源用户的需求。
- 每日聚合首页能够显著提高使用价值。
- 本地优先、无账号能够满足个人阶段。
- Web 流程稳定后可以低成本封装为理想的 Android 体验。
- AI 生成、动作识别或食物识别能够解决核心问题。

这些内容不得在获得证据前写成确定需求。

## E. 风险

- 健身与营养涉及健康风险，产品不能把一般性建议包装成医疗判断。
- 如果同时实现两个完整领域，首版范围可能失控。
- 如果先选技术或页面再理解场景，数据模型和交互会反复返工。
- 个人数据长期积累后，导出、迁移和隐私问题会变得关键。
- 营养数据存在品牌、地区、份量和许可差异。
- 朋友的目标和习惯可能与项目所有者明显不同，个人验证不能代替朋友测试。
- “持续使用”和“身体结果改善”不是同一件事，成功指标必须避免错误归因。

## H. 2026-08-20 产品文档重构审计发现

> 本节记录多智能体审阅发现，不直接构成产品事实；正式事实以重写后的 `docs/product.md` 为准。

- 当前产品稿的主要问题是信息架构，而不是能力数量：产品事实、运行约束、技术候选、代表场景和后续阶段任务混在同一层级，并存在多处重复。
- 重写需要统一术语并把内容归入产品定位、用户与演进、产品原则、能力地图、代表场景、当前运行约束和后续产出。
- 必须修正三项高优先级内容：
  - Android APK 是 Web 满意后的明确后续交付目标，不能写成仅“再考虑”。
  - 晚间训练与晚餐先后顺序是一个代表场景，但不能扩写为所有训练都发生在晚上；一般规则必须覆盖任意训练时段和当天是否还会继续进食。
  - 用户早期明确提出可以自己制定饮食计划；重写需保留该高层意图，但其具体含义留到领域规则阶段。
- “允许 IP + 端口访问”不能扩写成“不需要安全连接”；是否使用 HTTPS、VPN、公网或局域网属于技术设计。
- 产品层保留长期服务器、数据不进入公共仓库、部署后数据不丢失、Codex 受控异步处理和未来分析执行者可替换等约束；具体目录、卷、CLI、MCP 和数据库后移。
- 模型原始估算与最终采用值都保留，但 Phase 1 不规定是否必须逐餐点击确认或默认采用哪一个结果。
- README 对 `findings.md` 和 `product-decisions.md` 的角色说明与 `AGENTS.md` 不一致，需要在正式文档重写后同步修正。

## I. 2026-08-20 GitHub 仓库结构调研

> 本节记录外部项目的目录组织方式与可借鉴结论，不构成本项目的产品事实或技术选型。

- OpenAI Codex 仓库把主要代码工作区（如 `codex-rs/`、`codex-cli/`、`sdk/`）、文档 `docs/`、工具 `tools/` 和脚本 `scripts/` 分开；根目录保留入口文件、治理文件和构建配置。
- OpenAI Agents Python 仓库采用 `src/`、`tests/`、`examples/`、`docs/` 的常见分层，根目录的 `AGENTS.md` 主要描述代码结构、工程约定和验证命令，不承载产品设计正文。
- Immich 作为同时包含 Web、服务端、移动端和部署内容的开源应用，把 `web/`、`server/`、`mobile/`、`deployment/`、`design/` 和 `docs/` 分开。它适合说明项目扩大后的边界，但不适合原样复制到当前小型项目。
- OpenAI 的 Codex 文档说明 `AGENTS.md` 会按仓库根目录到当前工作目录逐层发现，越接近工作目录的指令优先，因此根级 `AGENTS.md` 应只保存全仓库长期有效的协作规则；未来代码子目录确有不同规则时再增加嵌套文件。
- 可迁移到当前项目的共同原则：运行代码进入 `src/`；长期有效的产品与设计资料进入 `docs/`；历史稿进入 `docs/archive/`；Codex 工作状态进入 `.planning/exercise-app/`；生成物和运行数据不进入源码与公开文档目录；根目录只保留项目入口、Agent 规则和工程配置。
- 当前项目不需要预先建立 `web/`、`server/`、`mobile/` 等空目录。等技术设计确认真实组件边界后再拆分，可以避免目录结构提前暗示尚未作出的架构决定。

上述“保持根 `src/`”的结论只解决了代码与文档分离，没有解决多应用边界，已被下一节在产品所有者纠正后形成的多应用仓库结论替代。

## J. 2026-08-20 多应用仓库架构复核

> 本节包含外部官方资料的研究摘要。资料只作为架构评估输入，不覆盖产品所有者的明确决定。

- 产品所有者指出上一轮只把代码和文档分开，仓库根目录仍由 Vite、TypeScript、前端入口和前端依赖配置占据，无法清楚容纳未来后端与 Android。这一纠正成立：当前结构仍是单前端应用结构，而不是产品级多应用仓库。
- npm 官方将 workspaces 定义为由顶层根包管理多个本地嵌套包的机制；根 `package.json` 声明工作区，根 `package-lock.json` 统一记录依赖关系，并可从根目录针对指定 workspace 执行脚本。来源：https://docs.npmjs.com/cli/v11/using-npm/workspaces/
- Android 官方结构把 Gradle 项目级配置、应用模块、源码资源与构建输出分开；本机 `local.properties` 不应进入版本控制，APK 位于模块的 `build/outputs/apk/`，属于构建产物而不是源码。来源：https://developer.android.com/build/android-build-structure 与 https://developer.android.com/build/build-for-release
- Capacitor 官方说明它可以加入既有现代 JavaScript 项目，使 Web 优先的产品使用原生容器并访问 Android 原生能力。这说明当前仓库应保留“复用 Web 的 Android 容器”和“未来独立原生实现”两种路线，而不在 Phase 1 提前锁定其中一种。来源：https://capacitorjs.com/docs
- 架构结论：采用单仓库、多应用边界。当前前端迁入 `apps/web/`；未来后端放入 `apps/server/`；未来 Android 工程放入 `apps/android/`。共享包和部署目录只在实际出现内容时创建，不创建空目录。
- 根目录的 `package.json` 改为 npm workspace 编排器，前端依赖与 Vite/TypeScript 配置归属 `apps/web/`；根目录只保留全仓库规则、入口、许可、锁文件和跨应用编排配置。

## K. 2026-08-21 Phase 2 领域规则依据

> 本节记录外部资料和由其推导出的设计约束。外部资料用于校准规则，不直接覆盖 `docs/product.md` 中已经确认的产品事实；具体算法、参数和地区数据源仍需在后续阶段验证与版本化。

### 营养目标与营养数据

- USDA DRI Calculator 使用年龄、身高、体重、活动水平及与公式相关的生理信息估算每日热量、宏量和微量营养素参考值，并明确说明个人实际需要可能高于或低于计算值。来源：https://www.nal.usda.gov/human-nutrition-and-food-safety/dri-calculator
- USDA FoodData Central 同时提供 Foundation、SR Legacy、FNDDS、Branded 等不同类型的数据集及字段说明；同一种食物的营养结果会受到数据类型、份量基准、地区、品牌和版本影响。来源：https://fdc.nal.usda.gov/download-datasets/
- NIDDK Body Weight Planner 根据当前身体信息、活动水平、目标体重和时间估算饮食与活动变化，说明训练活动变化可以影响能量需求，但结果仍是模型估计而不是个体测量。来源：https://www.niddk.nih.gov/bwp
- 领域规则需要保留营养数据的来源、类型、版本和份量基准；缺失营养项必须表示为“未知”，不能自动当作零参与完整性判断。

### 运动消耗估算

- 2024 Compendium of Physical Activities 使用 MET 提供标准化活动能量成本；其修正 MET 说明同时强调，标准 MET 会因年龄、体重、身高、生理特征、瘦体重和静息代谢不同而偏离个体实际值，Compendium 不是为精确测量个人运动消耗而设计。来源：https://pacompendium.com/ 、https://pacompendium.com/corrected-mets/ 及同行评审论文 https://pmc.ncbi.nlm.nih.gov/articles/PMC10818145/
- 因此运动消耗必须标为估算，记录方法、活动映射、输入、来源版本和假设；计划训练只能提供当天的临时参考，存在实际训练记录后应以实际时长和训练量更新估算。
- 日常活动水平和单次训练可能发生重复计算。领域模型必须明确某套计算策略是否已经包含计划或实际训练，禁止在不知情时把同一活动重复加入当天能量目标。

### 餐食图片估算

- 单张二维照片很难准确恢复距离、角度、深度、遮挡、隐藏油脂、烹饪方式和真实食用比例；额外文字或人工修正能够帮助处理这些信息，但不应成为上传和分析的强制条件。来源：https://pmc.ncbi.nlm.nih.gov/articles/PMC11607557/ 、https://pmc.ncbi.nlm.nih.gov/articles/PMC7686022/
- 现有图片饮食评估研究的任务、数据集和误差表达差异很大，不能把某个总体准确率直接套用到本产品；模型结果应保留候选食物、份量假设、营养来源、不确定性及原始结果。来源：https://pmc.ncbi.nlm.nih.gov/articles/PMC9194158/
- 由此推导：图片分析任务、模型原始估算、当前采用值和用户修订必须是不同概念；重试不能覆盖旧尝试，用户修正应重新计算对应餐食和当天汇总。

### 健康与安全边界

- 美国《Physical Activity Guidelines for Americans》把活动建议置于一般健康指导范围，并指出存在慢性疾病或特殊健康状况的人可能需要医疗专业人员协助选择适合的活动。来源：https://health.gov/paguidelines/second-edition/pdf/Physical_Activity_Guidelines_2nd_edition.pdf
- 产品应提供一般健身和营养参考，不进行诊断、治疗或个体医疗承诺；动作指导和估算结果不能表述为绝对标准、绝对安全或精确测量。

### 对领域文档的共同约束

- 所有计算结果都应能够说明“使用了什么输入、哪套方法、哪个版本和哪些假设”。
- 原始事实、系统推导、用户当前采用值和历史修订需要分开保存，不能只保留最后一个数字。
- 未记录、未知、待分析和确认为零是不同状态；数据不完整不阻断产品使用，也不能生成虚假的确定性结论。
- 数值点估计应在可行时同时提供合理范围、置信等级或限制说明；具体呈现方式属于 Phase 3，计算与状态含义属于 Phase 2。

## M. 2026-08-23 营养参考与训练联动计算研究

> 本节是 Phase 2 下一主题的研究输入，不直接构成已确认领域规则。具体方案将在完成来源核对后由 Agent 整体提交产品所有者纠正。

### 每日能量参考

- 美国国家科学院 2023 年《Dietary Reference Intakes for Energy》给出了 19 岁以上成人按年龄、性别、身高、体重和四级 PAL 分类计算的 EER 方程；EER 面向体重稳定成人，代表维持能量平衡的平均估计摄入。来源：https://www.nationalacademies.org/read/26818/chapter/7
- 成人方程的输入单位是年龄（年）、身高（厘米）、体重（千克），男性与女性、Inactive / Low active / Active / Very active 分别使用不同方程。报告给出的个体预测标准误可达到约 96–342 kcal/日，说明结果必须呈现为估算而非精确额度。
- 官方应用章节明确建议根据一段时间内的体重变化逐步校准摄入；同样身体参数的人，真实需要也可能明显偏离方程结果。如果用户在稳定活动下体重保持稳定，历史实际摄入可以帮助校准，而不是永远只依赖公式。来源：https://www.nationalacademies.org/read/26818/page/154
- 2023 EER 的 PAL 分类已经把身体活动计入总能量消耗，因此若再把单次训练的总消耗直接相加会存在重复计算风险。产品必须选择“习惯活动已含训练”或“非训练基线 + 显式训练调整”的一致策略。

### 宏量营养参考

- 国家科学院当前成人 AMDR 参考范围为碳水化合物占能量 45%–65%、脂肪 20%–35%、蛋白质 10%–35%；AMDR 是降低慢性病风险并满足必需营养素的总体范围，不是针对力量训练目标的唯一分配方式。来源：https://www.nationalacademies.org/read/27957/chapter/5 与 https://www.nationalacademies.org/read/10872/chapter/7
- 成人普通蛋白质 RDA 的通用参考为 0.8 g/kg/日；运动人群需要结合训练目标使用运动营养证据，而不是把 AMDR 百分比直接换成健身蛋白质目标。来源：https://www.nationalacademies.org/index.php/cdn/materials/9fb9fae6-337c-4b7c-9821-2c81d1f65ad0
- Academy of Nutrition and Dietetics、Dietitians of Canada 与 ACSM 的联合立场指出运动表现和恢复需要匹配训练情景的能量与宏量营养策略，并建议个性化运动营养计划由合格营养专业人员评估。来源：https://pubmed.ncbi.nlm.nih.gov/26920240/

### 初步设计含义

- 系统应先产生“维持能量参考”，再单独记录目标策略调整；减脂或增重不能偷偷混进 EER 本身。
- 蛋白质适合按体重与训练/目标规则计算，脂肪适合保留能量占比边界，碳水化合物适合承担满足总能量后的剩余分配；三者不能随单次训练消耗机械同比缩放。
- 训练联动需要明确定义基线 PAL 是否含训练。一个可解释候选方案是以不包含计划训练的日常活动作为基线，再用单次训练的净活动消耗更新当天能量；是否采用及如何估算净消耗仍需继续核对。

### 运动人群蛋白质

- ISSN 2017 蛋白质立场文件建议多数健康运动人群每天摄入约 1.4–2.0 g/kg 蛋白质，以支持训练适应；能量限制期间、以保留瘦体重为目的的阻力训练人群可能需要更高，但该高范围不应自动套用于所有用户。来源：https://pmc.ncbi.nlm.nih.gov/articles/PMC5477153/
- 2018 年包含 49 项研究、1863 人的系统综述与元回归发现，在阻力训练条件下，总蛋白质摄入超过约 1.62 g/kg/日后，对瘦体重增长没有观察到进一步总体收益。来源：https://pubmed.ncbi.nlm.nih.gov/28698222/
- 因此面向普通健身的初始系统建议可以把 1.6 g/kg/日作为中性默认点，把 1.4–2.0 g/kg/日作为可解释范围；特殊减脂、极低体脂、肾脏疾病或其他临床情况不能只靠应用自动提高目标。
- 每日蛋白质目标应主要由体重、训练类型和目标决定，不随当天估算消耗同比波动；当天训练联动更适合调整能量和碳水，而不是把蛋白质当作运动热量的剩余项。

### 运动消耗与重复计算

- 2024 Adult Compendium 以 1 MET ≈ 1 kcal/kg/小时作为标准化能量成本，活动总消耗可近似为 `MET × 体重 kg × 时长小时`。来源：https://pmc.ncbi.nlm.nih.gov/articles/PMC10818145/ 与 https://pmc.ncbi.nlm.nih.gov/articles/PMC11336313/
- 如果基础能量参考已经覆盖同一时段的静息消耗，把活动总消耗全额相加会重复计算至少 1 MET；单次活动的净增量候选公式为 `(MET − 1) × 体重 kg × 时长小时`。这仍是群体估算，不是个人测量。
- 2024 成人 Compendium 主要面向 19–59 岁；60 岁以上有独立 Older Adult Compendium，标准静息代谢换算不同。系统必须按年龄选择适用来源或停止输出个性化消耗，而不是跨年龄直接套用。

### 体重目标调整

- CDC 当前建议减重采用渐进、稳定的节奏，约每周 1–2 磅；药物、疾病、压力、激素等因素都可能影响体重管理。来源：https://www.cdc.gov/healthy-weight-growth/losing-weight/index.html
- ISSN 体成分立场认为减脂依赖持续能量缺口，起始体脂更低时应采用更慢速度以更好保留瘦体重；阻力训练备赛文献常见每周体重下降 0.5%–1.0%，但这不是所有普通用户的通用处方。来源：https://pmc.ncbi.nlm.nih.gov/articles/PMC5470183/
- NIH Body Weight Planner 使用当前体重、性别、年龄、身高、PAL、目标体重、目标时间与活动变化计算达到和维持目标所需能量，并明确活动变化会影响摄入需要。它比固定使用“每 7700 kcal 对应 1 kg”更适合作为减重动态模型的验证参考。来源：https://www.niddk.nih.gov/bwp
- 增肌所需最优能量盈余缺乏经过验证的统一值；2019 综述明确指出常见盈余估计尚未在阻力训练人群中验证。来源：https://pubmed.ncbi.nlm.nih.gov/31482093/
- 自然健美休赛期综述给出约 10%–20% 能量盈余和每周体重增加 0.25%–0.5% 的实践建议，但适用对象偏向健美训练者，不能直接成为所有用户默认值。来源：https://pubmed.ncbi.nlm.nih.gov/31247944/
- 产品应把减脂/增重速度和能量调整标为可校准策略：先给保守建议，结合连续数周体重趋势逐步修正；不能声称公式能准确预测个体体重变化。

### 审计结论与修正方向

- 当前引用集合的来源质量整体可评为高，约 85/100；但上一轮整套计算方案包含多项跨资料推导，作为产品算法的整体置信度只宜评为约 65–75/100。根据产品所有者随后确认的“规划准确性优先”要求，这个整体水平不足以成为正式规划算法；低置信产品策略必须与高置信核心计算拆开，继续验证或提供显式可调选项。
- 高置信部分可作为规划核心候选，仍需保留适用范围、来源版本、公式测试和个体校准；中低置信部分不能借用权威来源的名义包装成确定规则。
- 面向当前主要用户，应把中国营养学会 2023 DRIs 和国家卫健委现行指南作为一般营养与中国成人体重管理的第一层依据；National Academies、NIDDK 和国际运动营养证据用于公式交叉验证与训练场景补充。
- 不把 1.62 g/kg 描述为蛋白质收益的确定阈值；更合适的表达是普通健康阻力训练者的参考中心约 1.6 g/kg，常见证据范围约 1.4–2.0 g/kg，并根据目标、饮食可行性和健康状态调整。
- 不把每周增重 0.25%–0.5%、脂肪固定 25%、训练增量主要分配给碳水或周均训练重分配写成外部共识；这些都应明确标为待验证的产品策略。
- 图片多模态模型的“可调用”与“能可靠估算营养”必须分开。后者在完成食堂餐样本基准测试前没有可接受的准确度结论，只能输出暂定采用值并允许用户修正。

## O. 2026-08-23 规划准确性与识别准确性分层

- 产品所有者纠正了置信度审计后的产品含义：多模态能力与营养识别准确度确实独立，但识别不确定性不影响系统设定每日目标和阈值。
- 系统提供的每日能量与营养目标属于规划基准，必须优先保证依据选择、适用人群、公式、输入、单位、边界和训练联动计算正确；这一优先级高于餐食识别准确性和当前实现便利。
- 照片分析是对“实际吃了多少”的估算。它的不确定性只传播到已摄入、剩余量和超出量的判断，不传播回每日目标本身，也不能成为降低规划算法标准的理由。
- “规划准确”不等于承诺系统能直接测量个人代谢或提供医疗处方。正确含义是：在明确适用范围内采用当前可靠证据，忠实实现公式，避免重复计算，并通过测试样例和版本记录保证结果可复核；个体差异继续通过合理适用范围和后续校准处理。
- 因此 N 节对多模态识别准确度“未建立”的结论只约束餐食估算验证，不构成推迟或降低每日营养目标计算规则的理由。

## P. 2026-08-23 高准确性优先的营养规划方案 v2

> 本节是依据产品所有者纠正后形成的完整 Phase 2 候选方案，等待整体纠正。它只定义计算责任和规则，不锁定代码库、SDK 或页面实现。

### P.1 三层结果严格分开

1. **规划基准：** 系统根据个人档案、目标和训练安排计算每日能量与营养目标，不读取餐食照片结果来决定“应该吃多少”。
2. **实际摄入：** 手工记录或图片模型估算“已经吃了多少”；模型不确定性保留在摄入结果中。
3. **比较结果：** `剩余或偏差 = 规划目标 − 当前采用的实际摄入`。摄入不完整或含暂定值时，只降低比较结果的完整性和置信程度，不修改规划目标。

### P.2 规划证据顺序

- 一般中国成人的能量与宏量营养基线优先使用中国营养学会 2023 DRIs；国家卫健委现行体重管理与成人肥胖指南用于其明确覆盖的人群和目标。
- 中国健康成年人运动消耗优先使用 T/CSSS 002—2023；活动不在该标准内时才使用年龄适用的 2024 Compendium，并明确标记为国际补充来源。
- National Academies 2023 EER、NIDDK 动态体重模型和国际运动营养系统综述用于补足中国公开资料缺少的个体化公式或训练情景，并作为交叉核验，不与中国参考简单取平均。
- 叙述性综述、特定健美人群建议和模型供应商文档不得成为每日规划核心数值的唯一依据。
- 同一指标只能有一个当前主计算方法；备用方法只用于资格不匹配、来源不可用或对照检查，不能静默切换。

### P.3 能量规划分为周预算和日分配

系统内部保留以下可解释组成：

`周能量预算 = 7 × 维持能量参考 + 周目标策略调整`

`某日规划目标 = 周能量预算 ÷ 7 + 当日训练净消耗参考 − 该周日均训练净消耗参考`

- **维持能量参考：** 首选适用于当前用户的中国 DRIs 方法；精确转写官方输入、单位、年龄、性别、生理状态和 PAL 定义。若缺少必要信息，不使用虚构默认值生成个性化结果。
- **周目标策略调整：** 维持为零；减脂或增重单独计算并保留来源、目标速度与方法版本，不能藏进维持能量。
- **日分配：** 把周预算按训练安排在一周内重新分布。训练日高、休息日低，但按原计划完成时七天总和仍等于周预算；这是一项透明的分配策略，不宣称人体必须每天完全补回运动热量。
- **无稳定周训练参考：** 系统仍可给出稳定的每日规划目标，但不伪造精细的训练日/休息日差异；用户形成计划或典型周后再启用日分配。
- **计划变化：** 训练前使用计划净消耗；训练中使用“已完成实际 + 尚未完成计划”；完成、放弃或取消后使用最终实际。相同训练只计一次。

采用“相对周均训练量”的原因是：维持能量方法中的活动水平通常已经反映习惯活动，直接再加整次训练容易重复计算；只分配某日相对周均值的差额，可以在不改写周总目标的情况下满足训练多则当天多吃、训练少则当天少吃的产品要求。

### P.4 运动消耗只服务活动差额

- 对 18–64 岁健康中国成人，活动与 MET 映射优先采用 T/CSSS 002—2023；其他年龄或未覆盖活动使用明确适龄来源，否则不输出伪精确数字。
- 同时保存总活动消耗和净活动消耗；用于日目标调整的是扣除同一时段静息消耗后的净活动部分，避免重复加入静息能量。
- 每次估算保留活动代码、强度、实际或计划时长、采用体重、来源版本和适用范围。
- 力量训练、间歇训练和无法可靠计时的活动允许给中心值与范围；范围影响当日目标的活动调整部分，不影响维持能量和宏量营养基础规则。

### P.5 目标策略

#### 维持体重

- 周目标策略调整为零，是最高可信和最容易校准的路径。
- 持续体重趋势明显偏离维持目标时，只提出校准建议；未经用户确认不静默改写当前算法或历史目标。

#### 减脂

- 对国家卫健委指南明确覆盖的超重或肥胖成人，优先按目标时间使用动态体重模型求解能量缺口，并用中国现行指南的速度、缺口和最低安全边界作资格检查。
- 当前中国指导原则对多数超重或轻度肥胖成人给出约每周 0.5–1 kg、每日减少 500–1000 kcal 或约 30% 总能量的范围。系统默认从范围的保守端开始，而不是自动选择最大缺口。
- 不符合该指南人群范围、存在相关疾病、孕期/哺乳期或结果触发安全边界时，不把肥胖管理参数直接套用为普通健身计划；保留手工目标和一般参考，并提示需要专业评估。
- 不使用固定“7700 kcal 等于 1 kg”直接推算长期计划；使用能够反映体重变化后能量需求变化的动态方法。

#### 增重或增肌

- 当前没有与维持或减脂同等级的权威公式能够保证能量盈余转化为肌肉，因此系统必须把“总体重增加计划”和“肌肉增加目标”分开表达。
- 使用动态体重模型或保守小幅盈余生成初始体重增加路径，再结合抗阻训练记录、数周体重和腰围趋势校准；不能承诺增加的体重都是肌肉。
- 每周增重 0.25%–0.5% 和 5%–20% 盈余只能作为较低等级的运动人群候选范围，不直接写成所有用户的高置信默认值。正式默认值需要继续核对或由产品所有者接受为保守产品策略。

### P.6 宏量营养分配

- **蛋白质先确定：** 无规律训练时采用中国 DRIs 对应年龄与性别参考；健康、规律运动成人使用运动营养证据，普通阻力训练以约 1.6 g/kg/日作为参考中心、1.4–2.0 g/kg/日作为可解释范围。1.62 g/kg 不是确定阈值。
- **蛋白质计算体重必须可解释：** 正常适用范围内可使用当前体重；肥胖、明显低体重或可靠瘦体重数据存在时，不能无条件用实际体重相乘。应采用有直接依据的调整体重、目标体重或瘦体重方法；方法未确认前不输出伪精确高蛋白目标。
- **脂肪保留范围与中心：** 一般中国成人优先遵守中国 DRIs 的脂肪供能范围；系统可以用范围中点形成单一规划值，但必须标明中点是分配规则而非唯一生理最优点。
- **碳水承担剩余：** 在蛋白质和脂肪约束满足后，用剩余能量计算碳水。训练日能量变化优先反映到碳水，是为了保持蛋白质目标和脂肪基础稳定；这是明确的分配策略，不冒充唯一医学结论。
- **约束冲突不得静默修正：** 若总能量太低，导致蛋白质目标、脂肪范围和碳水范围无法同时满足，系统不挤压某一项后继续显示“达标计划”，而是标记目标组合不成立并回到能量或目标速度校正。
- 克数与能量换算采用明确、版本化的换算常数；宏量营养换算后的能量总和必须在舍入容差内等于当日能量目标。

### P.7 规划算法的验收门槛

一套方法只有同时满足以下条件，才能从候选升级为正式规划算法：

1. 有能够直接支持该公式或范围的原始官方资料、共识报告或高质量系统综述。
2. 明确适用年龄、性别、生理状态、健康状态、目标和所需输入；缺失时不偷偷填默认值。
3. 公式、单位和舍入通过官方示例或独立计算样例复核。
4. 同一训练、静息能量和 PAL 不重复计算。
5. 七日目标在没有计划偏差时严格回到周预算；计划与实际变化只影响应变化的日期和组成。
6. 蛋白质、脂肪和碳水换算后与能量目标一致；约束冲突能被检测。
7. 每次结果保存输入快照、来源、方法版本、生成时间和组成，能够重现。
8. 以边界样例验证正常体重、超重、肥胖、低体重、缺失输入、无训练计划、训练取消、少练、多练及跨日训练。

### P.8 当前仍不能伪装成已解决的事项

- 中国 DRIs 2023 个体能量方法的正式转写与示例校验，需要在实现前取得并逐项核对完整官方表格或正文；当前不能凭二手摘要手抄公式。
- 肥胖或明显低体重时的蛋白质“计算体重”选择需要继续锁定适合本产品人群的直接依据。
- 增肌初始盈余没有与维持、减脂同等级的强证据，必须采用保守、可校准且明确降级的策略。
- 训练日额外能量全部还是部分当天分配，属于产品分配政策；使用相对周均值能够保证周预算守恒，但最终系数仍需产品所有者整体确认。

## AB. 2026-08-24 Redis 与异步任务架构复核

- 产品所有者提出可以考虑 Redis，因此 Phase 4 不再把“个人阶段不增加 Redis”视为默认结论，改为重新比较 PostgreSQL 内队列和 Redis 队列。
- Redis 官方提供 RDB、AOF、两者结合或无持久化四类策略；AOF 默认每秒同步时仍可能丢失约一秒写入，RDB 快照可能丢失最近数分钟。因此即使采用 Redis，也不能把唯一业务记录或无法重建的分析任务只保存在 Redis：<https://redis.io/docs/latest/operate/oss_and_stack/management/persistence/>。
- BullMQ 官方确认它是建立在 Redis 上的 Node.js 队列，支持延迟任务、周期调度、失败重试、并发控制和进程崩溃恢复；官方同时明确最坏情况下是至少一次投递，所以 Worker 仍必须幂等，不能依赖“恰好一次”：<https://docs.bullmq.io/>。
- BullMQ 的去重 ID 能减少同一未完成任务的重复入队，但手工删除作业会取消去重状态；它只是一道运行保护，不能替代 PostgreSQL 中的唯一约束、任务状态和采用值保护：<https://docs.bullmq.io/guide/jobs/deduplication>。
- BullMQ Job Scheduler 会在上一个作业开始处理后再生成下一项；队列繁忙或 Worker 不足时，实际触发频率可能低于配置频率。因此提醒意图和到期时间应保存在 PostgreSQL，由调度任务扫描到期记录，不能只把用户提醒定义保存在 Redis：<https://docs.bullmq.io/guide/job-schedulers/>。
- Redis 官方安全文档警告不得把 Redis 端口暴露到不可信网络；生产部署应只允许内部网络访问，使用 ACL 最小权限和认证，Redis 不对公网开放：<https://redis.io/docs/latest/operate/oss_and_stack/management/security/>、<https://redis.io/docs/latest/operate/oss_and_stack/management/security/acl/>。
- 当前更稳妥的候选不是让 Redis 取代 PostgreSQL，而是采用“PostgreSQL 业务真相 + 事务 outbox + Redis/BullMQ 执行队列”：业务事务同时写任务和 outbox，分发器把仅含任务 ID 的消息送入 BullMQ，Worker 每次回到 PostgreSQL校验归属、状态和幂等条件；Redis 清空后可从未完成任务和 outbox 重建队列。
- BullMQ 的生产指南要求 Redis 启用持久化，并把 `maxmemory-policy` 设为 `noeviction`，否则任意逐出队列键会破坏队列行为；生产者应在 Redis 断开时快速失败，Worker 则持续重连：<https://docs.bullmq.io/guide/going-to-production>。
- BullMQ 提供全局队列限流，也能在供应商返回 `429` 时手动把任务重新放回等待状态；这比在各 Worker 内各自计数更适合约束视觉 API 的总调用速率，但具体限额仍以供应商实时配置为准：<https://docs.bullmq.io/guide/rate-limiting>。
- PostgreSQL 18 官方说明 `FOR UPDATE ... SKIP LOCKED` 适合多个消费者避免队列表争用；outbox 分发器可据此并发领取待投递记录，但必须使用确定排序、租约/重试和投递幂等，不能把 `SKIP LOCKED` 当成完整队列实现：<https://www.postgresql.org/docs/18/sql-select.html>。
- Redis 8 及后续版本提供 RSALv2、SSPLv1、AGPLv3 三种许可选择，其中只有 AGPLv3 是 OSI 批准的开源许可；BullMQ 本身为 MIT。当前项目不修改或嵌入 Redis 源码，但开源发布前仍需在第三方许可清单中说明独立 Redis 服务与选用许可，避免把 Redis 服务器误写成项目 MIT 代码的一部分：<https://redis.io/legal/licenses/>、<https://docs.bullmq.io/>。
- 综合个人部署与未来朋友使用，Redis 的价值主要不是当前吞吐量，而是把视觉 API 的并发、重试、退避、延迟和限流从业务数据库轮询中分离；代价是一项额外有状态服务和 PostgreSQL→Redis 的一致性交接。只有采用可重建队列与 outbox，收益才大于这项复杂度。

## AC. 2026-08-24 pg-boss 专项可靠性复核与确认
