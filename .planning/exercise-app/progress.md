### Phase 1 访谈：现实饮食场景

- **状态：** 进行中
- 用户主要吃食堂餐，缺少可直接录入的配方、份量和营养信息。
- 用户希望记录饮食，但当前场景使手动记录难以执行。
- 首要问题候选曾被误缩小为“记录食堂餐”，已根据用户纠正。
- 产品准确性边界初步明确为“可修正的近似估算”，不是精确营养检测。
- 用户真正期望的是“计算每日目标 → 拍照估算每餐 → 累计并对照目标”的完整闭环。
- 食堂只是重要使用场景，不是产品目标。
- 用户进一步明确：训练和饮食各自独立，但训练量需要影响当天饮食目标。
- 规划已从“首版只选一个领域”修正为“验证最小的跨模块价值闭环”。
- 用户说明训练通常在晚上，联动必须考虑当天时间和进餐状态。
- 已确认首个状态规则：先按训练计划生成暂定营养目标；训练取消后，晚饭未吃则下调剩余额度，已经吃过则提醒偏差。
- 用户明确训练提醒与饮食超标提醒是两类独立提醒。
- 联动只改变目标和状态数据，不混淆两个模块的提醒职责。
- 下一步：汇总当前结论，形成并确认 Product Brief v0.1。

- 当前推荐的首选交接方案是“服务器待分析队列 + 项目专用命令行工具”；MCP 作为后续可选集成方式，具体技术选择留到 Phase 4。
- 产品所有者明确，日常手机拍照意味着个人阶段就需要长期运行、手机可访问的服务器，而不是仅在本地临时运行 Web 应用。
- 产品全貌已补充运行与数据前提：照片和业务记录与 GitHub 源码分离，存放于不会被重新部署覆盖的持久化数据位置，并要求考虑备份与恢复。
- 产品所有者纠正部署访问假设：个人阶段可以直接使用服务器 IP 和端口，域名与 HTTPS 不作为产品必备条件，具体连接和安全方式留到技术规划阶段。
- 已将本轮讨论从零散约束整理为个人阶段拍照估餐运行设计：手机上传、服务器持久化、待分析记录、用户发起 Codex、受控读取、结果回填、确认修正和重新汇总。
- 设计明确 GitHub 只保存可公开项目内容，运行数据不进入仓库；应用代码可以重新部署，照片和记录必须持续保留。
- 新增稳定决定 D-009：在没有多模态 API 的阶段，拍照估餐采用可被未来识别服务替换的异步 Codex 流程。
- 产品所有者确认个人信息变化规则：体重或健身目标更新只影响当天及之后的计算，过去记录和当时目标保持原样，不重新计算历史。

- 训练计划与实际记录分离；实际动作和训练量由用户训练时录入，临时变化不自动改写原计划。
- 产品所有者确认餐食照片支持可选文字说明，用于补充份量、隐藏食材或实际食用比例；文字不是保存和分析的必填条件。
- 产品所有者确认没有照片或无法分析时允许手动录入；不输入也不影响程序正常使用，不产生强制补录要求。
- 产品所有者确认支持常用食物和常用餐食，方便手动录入时复用已有结果并调整当天份量。
- 产品所有者确认模型原始估算和用户最终采用值都保留；营养统计只使用最终采用值。
- 产品所有者确认朋友阶段采用同一服务器上的独立账号，每位用户的档案、训练、饮食和照片默认相互隔离。
