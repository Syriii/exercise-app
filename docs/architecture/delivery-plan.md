### 能力差距与验收场景

本表不规定工期，也不把可靠性修复混同于域名/HTTPS 工作。图片识别仍是用户指定的功能优先项，依赖的食物基准、单项结构与恢复规则需要一同交付。代码证据见 [2026-09-05 审查报告](../../.planning/exercise-app/design-code-audit-2026-09-05.md)；以下均待实现或待新流程验证。

|---|---|---|
| F01 | 单项照片结果及自动记餐 | 包子、鸡蛋、豆浆形成可单独改量/移除/复用的条目；无手工结果时成功自动计入，不要求确认；混合菜不伪造原料拆分 |

| F06 | 独立日期安排与多周编排 | 安排时保存副本；改可复用计划不影响周一/周四既有安排；改周一不改周四；各周可不同；改期/取消/删计划不移动或删除已有实际 |

| F08 | 首次设置与我的 | 前三步必要、提醒可跳过；未完成续填、已完成不重复、已有用户衔接；计算不适用仍可记录；我的摘要目录与低频账号设置分层 |
| F09 | 身体记录时间与删除 | 先记当天再补旧日期，不以录入时间选最新（C2）；只改备注不改测量时间；删除后选择最近有效值；我的/历史共用编辑与趋势，旧参考不批量回算 |

| F11 | 跨页草稿、时间和失败路径 | 入口日期传递、过去日期提示、跨午夜不改草稿；同账号登录恢复、并发冲突保留输入、账号切换不泄露草稿；重复提交只生成一次事实 |
| F12 | 提醒与低频工具衔接 | 三类独立提醒按时间/周期；不依赖开始训练、全天覆盖或饮食剩余；密码、导出、退出、删号、主动问题报告、管理员入口可用且权限不扩大 |
| F13 | 旧数据前向兼容 | 原方案/周期、已存实际训练、餐食与修订仍可读；旧整餐不能可靠拆分时保留组合记录；旧计划量不能自动迁为实际；新旧贡献不双计 |

### 进入代码后的质量门

- 按真实依赖形成可运行切片，不能只改按钮和导航来宣称 F01–F13 完成；具体切片编排在文档审阅后写入唯一任务计划。
- 每批运行类型检查、相关单元/API 合约和构建；核心流程增加手机浏览器 E2E，覆盖正常、空白、失败、返回、编辑、删除和跨日。
- 涉及数据和任务时，使用名称以 `_test` 结尾的显式隔离 PostgreSQL 测试库验证事务、RLS、升级、任务接管和重复写回；内存复现不能替代真实 PG 验收。
- 新私有表或关联必须同步访问分类、跨账号拒绝测试、RLS、导出与删除；草稿不能落入问题报告或脱敏日志。
- 原有营养/训练规划公式与证据本轮不改，保留其回归；真实图片供应商的单项输出需单独合约与经授权样本验证，不以模拟估算冒充真实识别效果。
- migration 先形成可审阅 SQL 与旧数据测试。生产 setup/migration、数据写入等不在常规受限重新部署授权内，需要按既有规则说明影响并另获授权。

## 1. 交付原则

- 每个增量都必须能启动、迁移、测试，并留下可继续使用的数据；
- 先打通真实纵向流程，不用静态页面冒充已实现能力；
- 规划公式的证据和测试优先于图片识别效果；
- 已确认的完整产品能力不会因首个版本较小而被删除，只是按依赖排序；
- 个人使用不设置天数、打卡次数或记录配额；观察只用于发现问题；
- 朋友、开源与 Android 都在同一架构上增量完成，不另起仓库或复制业务规则。

## 3. 增量 0：工程与数据地基

### 范围

- 创建 `apps/server/` 模块化单体与 API/Worker 两个进程入口；
- 建立 PostgreSQL、Drizzle migration、pg-boss 后台队列、自有任务/尝试表和临时媒体存储接口；
- 建立预置 `admin` 管理员的安全初始化、常规注册、登录、退出、会话撤销、当前账号和注册开关接口；
- 在“设置”中建立仅 `admin` 可见的最小系统管理页，覆盖注册开关、账号状态、会话撤销和基础服务健康；
- Web 加入 Vue Router、Pinia 和类型化 API 边界，现有原型拆为真实路由；
- 建立 Docker Compose 开发/个人部署骨架、health check 和 secret 模板；
- 建立单元、数据库集成、API 合约和浏览器端到端测试入口；
- 建立备份与恢复烟雾测试，不包含真实业务数据。

### 完成条件

- 新服务器上可通过私密初始化配置建立 `admin` 的初始密码并完成首次登录换密；普通用户可在注册开放时通过标准页面创建账号；
- 登录后刷新页面仍保持会话，退出或撤销后旧会话失效；
- 数据库只包含 Argon2id 摘要而没有密码明文或可逆密码；注册、登录、失败响应、日志和备份清单均通过防泄漏测试；
- 首个普通注册用户不会获得管理员权限；管理员默认不能通过产品接口读取其他账号的训练、饮食或临时照片；
- 普通用户看不到系统管理入口且直接访问管理 API 返回无权限；管理员操作有审计记录，敏感 secret 和破坏性数据库操作不进入网页；
- 容器重建后数据库和仍处于有效处理期的测试照片存在；
- migration 可从空库前滚，备份能恢复到临时环境；
- 事务提交后任务可执行、事务回滚后没有孤儿任务；Worker 被强制终止或数据库短暂断开后任务可恢复且不会重复写入业务结果；
- 仓库和构建产物中没有真实 secret、数据库、照片或备份；
- 跨账号访问的基础测试从这一增量开始存在。

## 4. 增量 1：训练闭环

### 范围

- 动作条目和许可安全的指导元数据；
- 本增量内部先完成“单次方案 → 实际训练”的简易闭环，再在同一数据边界上增加周期计划编辑器，避免两种复杂度同时进入首轮实现；
- 用户建立、编辑、复制、归档多个不同目的的单次训练方案，不要求绑定固定星期，也不提供同一方案的编辑版本历史浏览；
- 用户建立任意周数、每周内容可不同的周期计划；训练单元可独立编辑或从单次方案导入副本，并允许对尚未开始的单元主动重新导入刷新；
- 用户可以提前为某日安排单次方案、周期训练单元或训练主题，也可以训练时任选一个方案或从空白开始；
- 从本次选中方案的动作勾选完成，录入实际组次、重量、次数和感受，并添加额外动作；
- “今天还要练”只显示当天已安排或本次已选择方案中的未完成动作，不把整个方案库算作任务；
- 记录训练开始/结束时间和取消/未训练事实；
- 按日期查看长期保存的实际训练和修订后的当前有效记录；默认展示实际动作与训练量，必要计划上下文只在详情中出现；
- 训练提醒独立配置和显示。

### 完成条件

- 不依赖系统建议也能完成“计划 → 实际 → 今日剩余 → 历史”闭环；
- 任一方案被后续编辑时，已有实际训练及其必要方案快照不会丢失或被错误改写；
- 修改源单次方案不会自动改变周期计划；重新导入只影响用户明确选择且尚未开始的训练单元，并在覆盖本地调整前确认；
- 额外动作与计划动作都能正确进入实际记录；
- 未填写可选数据不阻断使用，且未知值不被保存为零；
- 时间、时区、并发修正和历史修订测试通过。

## 5. 增量 2：官方规划引擎

### 范围

- 当前个人档案、身体测量时间序列、当前目标和当前策略；页面不提供通用版本浏览，当前采用体重同时显示测量日期；
- 实现 `calculation-evidence.md` 已确认的每日能量、蛋白质、脂肪、碳水参考及安全停止条件；
- 实现实际训练运动消耗估算，并保存体重、动作/强度来源、时长、方法版本和结果范围；
- 实现系统训练建议候选；采用、编辑或放弃后只生成用户计划；
- 实际训练只更新训练事实与未完成项目，不改变当日系统营养参考；页面持续并列展示剩余摄入和未完成训练；
- 保存输入快照、证据 ID、方法版本、结果、警示和舍入；
- 对证据覆盖不足或特殊状态停止自动个性化，允许继续手工记录。

### 完成条件

- 每项规划数值与运动消耗估算都可从界面追溯到输入、方法版本和官方依据；
- 官方测试夹具、边界值、单位和舍入测试全部通过；
- 图片、语言模型或用户历史估算不能改变规划公式；
- 相同输入与方法版本得到相同结果，旧历史不因方法升级静默变化；
- 缺少必要资料时明确说明缺什么，但训练和饮食记录仍可继续。

## 6. 增量 3：手工饮食闭环

### 范围

- 系统营养建议、官方支持的策略选项和适用范围；
- 食物搜索、常用项、最近使用项、份量选择和手工填写；
- 餐次与日期记录；盛取量、实际摄入量和未知值分开；
- 记录来源、食物数据版本和包装标签来源；
- “今天还能吃多少”持续显示系统参考减去当前有效摄入；超过时明确显示超出，不显示负的“还能吃”；
- 饮食提醒独立配置；
- 按日期查看饮食历史并修正旧记录。

### 完成条件

- 完全不上传照片也能完成一日饮食记录；
- 搜索无结果时可立即手工填写，不阻断食堂场景；
- 同一食物的份量、营养来源和采用值可解释、可修正；
- 删除或修正餐食后当日汇总事务性更新；
- 食物数据许可经过登记，受限数据库没有进入公开仓库。

## 7. 增量 4：拍照异步估餐

### 前置门

DeepSeek 官方“图像理解”指南已经满足图片输入文档要求，`deepseek-v4-flash-vision-exp` 是首个实现的视觉提供方。开始真实接入前仍需使用项目自己的 API key 完成最小契约验证，覆盖 Base64 图片、结构化响应、用量、超时、限流和错误分类；验证失败时不把模拟结果标成真实模型能力，也不阻塞手工记餐。

### 范围

- 手机拍照或相册上传、图片压缩提示、上传进度和重试；
- 照片可靠暂存、权限读取、确认后删除、到期删除与孤儿清理；
- 任务、尝试、超时、退避、最近任务结果和已有候选并存；
- 视觉提供方适配器、结构化 Schema、原始结果与用量记录；
- 候选食物、份量假设、营养范围、不确定性和待确认项；
- 用户修改并采用；任何新模型结果不得静默覆盖当前采用值；
- 用户确认、修正到满意结果或放弃分析后异步删除原图；删除失败可重试且不影响结构化结果；
- Codex 或人工复核结果通过受控入口进入同一候选流程。

### 完成条件

- 上传后关闭或切换页面不影响任务，重新进入能看到真实状态；
- 重复请求、Worker 重启、限流、超时和永久失败不创建重复餐食；
- “旧候选仍存在 + 最新任务失败”能同时表达；
- 删除餐食后迟到模型结果不能恢复数据；
- 模型结果不能进入系统目标计算，用户修正始终优先；
- 日志、错误和公开测试夹具不泄露真实照片或模型原始内容。
- 普通重启不丢失处理中照片；原图删除后模型原始结果、当前采用值和修订仍可完整使用。

## 8. 增量 5：个人长期使用版

### 范围

- 生产 Docker Compose、IP + 端口的可信私网部署说明和公网 HTTPS 边界；
- 独立的训练、饮食和身体测量应用内提醒，以及支持时的浏览器通知；体重采用每周一次的可配置默认值，允许暂缓或关闭；
- 自动备份、异机副本、恢复演练和状态提示；临时原图默认不进入长期备份；
- JSON + 生命周期清单导出、账号删除与清理状态；
- 结构化日志、任务健康、存储异常和磁盘余量提示；
- 管理员系统管理页补齐模型、任务、临时媒体、磁盘、备份和恢复验证摘要；
- 真实手机和桌面浏览器回归，处理个人使用中发现的问题；
- 数据迁移、版本升级和失败恢复说明。

### 完成条件

- 服务器重启和应用升级后可继续使用；
- 最近一次备份和恢复验证时间可见，能够在另一临时实例恢复；
- 日常核心流程不依赖开发工具或手工改数据库；
- 模型不可用时仍可手工记餐；规划引擎不可计算时仍可记录；
- 产品所有者按自己的频率使用并确认满足个人日常需要。这里不设置使用天数或打卡数量门槛。

## 9. 增量 6：朋友与开源版

### 范围

- 每个账号独立导出与删除；

- 发布前去除个人配置、真实内容和不可再分发数据。

### 完成条件

- 自动化测试证明账号 A 无法读取、修改、推断或下载账号 B 的任何私有记录；
- 新用户只按 README 和部署文档即可启动；
- 默认配置不暴露数据库、照片目录或管理接口；
- 开源仓库扫描不含 secret、真实日志、照片、备份或受限数据；
- 第三方服务、食物数据和动作内容的许可与隐私边界清楚。

## 10. 增量 7：Android APK

### 迁移验证

先在 `apps/android/` 建立最小 Capacitor 验证，不直接承诺完整 APK。必须验证：

- Vue 构建与五个入口在 WebView 中的布局、返回键和深链接；
- 相机拍照、相册选择、权限拒绝、图片大小和后台恢复；
- 服务端会话的安全传输与本机安全存储；
- 弱网、网络切换和上传重试；
- 本地通知权限、时区和重启后的提醒；
- 目标 Android 版本的签名、安装和升级保留数据。

### 正式范围

- 复用 Web 业务页面和服务端 API；
- 接入相机、通知、网络状态和必要的原生生命周期；
- 建立 debug/release 构建、签名密钥私密管理和 APK/AAB 产物流程；
- 回归训练、手工饮食、拍照任务、历史和设置；
- APK/AAB、Gradle build 和签名文件都不进入 Git。

### 完成条件

- 在目标 Android 设备独立安装和升级成功；
- 拍照到采用结果、训练记录和提醒核心流程可用；
- 网络中断不会丢失已由服务器确认的数据，也不会重复创建记录；
- 签名、版本号、隐私权限和发布说明完整；
- 如果 Capacitor 验证失败，先形成具体差距报告，再决定局部原生插件或原生客户端，不静默降低需求。

## 11. 跨增量质量门

每个增量进入下一项前共同检查：

1. 当前数据库从空库 migration 成功，已有测试数据升级成功；
2. 根目录 `npm run check` 与 `npm run build` 通过，并运行该增量新增测试；
3. 核心正常、空白、等待、失败、修正和安全边界状态有对应测试；
4. 新增数值规则已登记官方依据、适用范围与方法版本；
5. 新增外部依赖记录官方文档、固定版本、许可和替换边界；
6. 新增私有数据没有进入日志、测试快照、镜像层或仓库；
7. README、AGENTS、架构、决策和部署说明与实际行为一致；
8. 可运行版本有备份，并验证恢复或至少完成该增量要求的恢复测试。

## 12. 风险门与不阻塞项

| 风险 | 处理 | 是否阻塞现在确认架构 |
|---|---|---|
| DeepSeek 视觉模型是实验版本，接口、价格或稳定性可能变化 | 以官方 Vision 指南实现独立适配器；固定模型 ID、记录用量并在增量 4 做真实契约测试 | 否；DeepSeek 可作为首个实现，适配器和人工补偿路径继续保留 |
| 公共食物数据覆盖与稳定性有限 | 首个 Open Food Facts 包装食品提供方按 ODbL 归属、每 100 克换算、字段过滤、缓存/限流与失败降级接入；中国常见食物等大型目录仍需逐项核对许可 | 否；个人、最近记录和手工录入始终可用 |
| Capacitor 的会话与后台行为尚未在目标设备验证 | 增量 7 先做迁移验证 | 否 |
| 单机 PostgreSQL 存在主机故障风险；未完成分析的临时照片不做长期备份 | 增量 5 完成业务数据异机备份和恢复演练；临时照片丢失时明确要求重新上传 | 否 |
| pg-boss 是第三方关键依赖 | 固定版本、真实 PG 测试、任务表与提供方边界可替换 | 否 |
| 服务器具体规格未知 | Phase 5 开始前采集并设置连接池、图片和 Worker 限制 | 否；不改变架构 |

## 13. Phase 5 完成与后续目标

增量 0–6 以及完成性审计发现的训练消耗、图片暂定采用、饮食安排、历史趋势和上传体验缺口，均已完成本地实现与自动化验收。Phase 5 Web 主体代码完成后，继续补充快速部署教程、应用内问题报告和部署侧诊断报告作为可运维性增量。真实服务器的 Compose 首次启动、PostgreSQL migration/RLS、API/Worker 健康、非破坏性 smoke 和外部 `IP:5011` 访问已经通过；pg-boss 故障恢复、DeepSeek 契约、备份与异机恢复继续作为独立专项验收。Phase 6 已加入 Open Food Facts 公开包装食品搜索；中国常见食物等大型公共目录仍等待合法数据源。获得实际使用反馈后，再决定体验修正并进入增量 7 Android 真机验证。
