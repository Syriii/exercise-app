## 1. 结论

本项目采用一个可逐步扩展的单仓库、模块化单体架构：

- Web 保持 Vue 3、TypeScript 与 Vite，加入 Vue Router 和 Pinia；
- 服务端使用 Node.js 24 LTS、TypeScript 与 Fastify 5；
- PostgreSQL 18 是业务事实、版本记录、账号会话和持久任务的主数据源；
- Drizzle 负责类型化数据访问和可审阅的 SQL migration；
- pg-boss 在 PostgreSQL 内执行图片分析、提醒、清理和导出等后台任务，个人阶段不增加 Redis；
- 餐食照片进入临时媒体存储接口，个人部署使用服务器持久目录或 Docker volume 保证处理期间不因重启丢失；用户确认、修正到满意结果或放弃分析后异步删除原图；
- Web 构建产物和 API 由同一个服务端入口提供，浏览器保持同源；Worker 使用同一服务端代码的独立进程入口；
- 图片分析通过可替换的视觉提供方适配器异步执行；任何模型结果都只是可修正候选，不参与系统规划公式；
- Web 满意后，优先用 Capacitor 将现有 Vue 应用装入 `apps/android/`，复用 API 和页面能力，再补相机、通知等原生能力。

这不是“先做一个浏览器临时页面，再重写正式系统”。个人版从第一天就使用真实账号、服务端、数据库、临时照片生命周期和长期业务数据备份边界，只把承载规模保持简单。

## 2. 架构目标

### 2.1 首要目标

1. **规划结果可追溯。** 每日训练建议和营养参考只由有官方证据、带方法版本的确定性计算产生。
2. **记录估算可修正。** 拍照识别、食物库和手工录入可以共同形成记录，但来源、假设、模型原始结果和当前采用值始终分开。
3. **个人部署简单。** 一台长期运行的服务器即可启动完整系统，并能备份和恢复。
4. **未来扩展不改核心模型。** 开放朋友、增加视觉供应商、迁移对象存储和封装 Android 时不重写训练、饮食和历史规则。
5. **私有数据不进入仓库。** 数据库、照片、备份、日志和密钥都属于运行数据。

### 2.2 明确不做

- 不把系统拆成微服务；
- 不把浏览器本地存储作为权威数据源；
- 不把 AI 输出当成营养目标或医学判断；
- 不在 HTTP 请求中同步等待图片模型完成；
- 不为尚未出现的跨应用复用预建 `packages/` 公共层；
- 不在个人版提前引入 Redis、Kafka、Kubernetes或独立对象存储集群；
- 不在 Phase 4 编写业务代码或创建空的服务端、Android 工程。

## 3. 系统全貌

```text
手机/桌面浏览器                         未来 Android（Capacitor）
       │ HTTPS 或可信私网 HTTP                  │ HTTPS
       └──────────────────┬─────────────────────┘
                          ▼
                 Web + API 同源入口
              Vue 静态文件 / Fastify API
                          │
              ┌───────────┼───────────┐
              ▼           ▼           ▼
         PostgreSQL   临时媒体存储   后台 Worker
       业务/会话/任务   待处理照片     分析/提醒/导出
              ▲                       │
              └───────────────────────┤
                                      ▼
                             可替换视觉模型 API
```

开发时 Vite 开发服务器代理 `/api` 到 Fastify；生产时服务端通过已固定修复版本的 `@fastify/static` 只提供公开 Web 构建目录，并提供 `/api/v1`，避免跨域和两套入口配置。用户照片永远不放在静态根目录。API 与 Worker 使用同一镜像和代码，只运行不同进程入口。

## 4. 应用与模块边界

### 4.1 `apps/web`

职责：

- 呈现“今天、训练、饮食、历史、设置”五个入口；
- 收集用户输入、照片和修正；
- 展示服务端返回的规划、记录、来源和任务状态；
- 在异步分析期间允许离开页面，并轮询任务状态；
- 只保存非敏感的界面偏好和短期草稿，不保存权威业务数据或认证令牌。

前端选择：

| 责任 | 选择 | 边界 |
|---|---|---|
| 视图 | Vue 3 单文件组件 | 保持当前基线 |
| 路由 | Vue Router | 一级入口有稳定 URL，可直接返回与刷新 |
| 客户端状态 | Pinia | 只放身份摘要、界面状态和跨页短期任务；服务端数据由 API 查询结果负责 |
| 构建 | Vite | 开发服务器与生产静态构建 |
| 类型检查 | `vue-tsc` + TypeScript 5.9 | 沿用当前已验证工具链，升级需整体验证 |

### 4.2 `apps/server`

服务端是一个模块化单体，模块之间只能通过公开服务接口或领域事件协作，不直接跨模块修改表。首批模块为：

- `identity`：注册、登录、账号、密码、会话、管理员权限、注册开关和账号状态；
- `profile`：当前个人档案、身体测量时间序列、当前目标、当前策略、时区和计算输入快照；
- `training`：系统建议候选、单次训练方案、周期训练计划及训练单元、可选日期安排、实际训练和必要的计划快照；
- `nutrition`：官方证据驱动的每日参考、策略、活动联动和计算快照；
- `meals`：餐次、手工食物、份量、照片和当前采用值；
- `analysis`：分析任务、尝试、供应商适配器、模型原始结果和采用操作；
- `history`：按日期聚合当前有效修订，提供来源与方法快照；
- `reminders`：训练、饮食与身体测量提醒规则、暂缓、投递和已读状态；
- `portability`：导出、删除、备份清单和恢复检查；
- `operations`：健康检查、任务维护、日志和管理操作。

系统每日营养参考和训练建议计算先留在 `apps/server` 的领域模块中。只有 Android 或其他应用确实需要在本地复用同一纯函数，并且不会形成两个权威计算端时，才提取到 `packages/`。

### 4.3 `apps/android`

Android 不是单独重写的第二套产品。首选路线是 Capacitor：

- 复用 `apps/web` 的 Vue 构建结果和同一套 API；
- Android 工程、Gradle 配置和原生权限只放在 `apps/android/`；
- 使用官方 Camera 与 Local Notifications 能力承接拍照和提醒；
- 照片分析仍由服务器执行，APK 不携带模型密钥和权威规划算法；
- 在正式迁移前做一次技术验证，检查相机权限、照片压缩与上传、会话、后台恢复和目标 Android 版本通知。

如果 Capacitor 验证不能满足这些核心场景，再评估原生客户端；这是一道迁移验收门，不是现在同时开发两套界面。

## 5. 数据架构

### 5.1 PostgreSQL 是唯一业务事实源

选择关系型数据库是因为当前领域存在大量外键、版本、唯一当前值、同账号归属和跨记录事务。核心原则：

- 每个私有业务根实体都保存 `user_id`；关联写入必须验证同一账号；
- 当前个人档案、目标和策略直接维护当前内容，身体测量按时间长期保存；历史依据由建议、每日参考和消耗估算各自保存的输入快照解释。计算方法和采用值仍按版本或修订保留；每个单次方案和周期计划只维护当前内容并可归档；实际训练长期保留并可修正；
- “当前值”由明确的当前修订指针或受约束状态表示，不靠查询时猜测最后一行；
- 数值保存统一单位、精度和舍入规则；克数、能量及计算快照使用 PostgreSQL `numeric`，不用二进制浮点作为权威值；
- 时间事实保存 UTC 时间戳及用户时区；“哪一天”按事件发生时的用户时区归档；
- 删除先使业务记录或临时照片引用失效，再异步清理原图和相应派生结果；迟到任务不得复活已删除数据。正常完成图片分析时只删除原图，不删除已采用的结构化结果。

朋友开放前，所有表和查询必须完成跨账号自动化测试，并在适合的私有表启用 PostgreSQL Row-Level Security 作为应用层授权之外的防线。

### 5.2 逻辑数据组

| 数据组 | 代表实体 | 必须保留的关系 |
|---|---|---|
| 身份 | user、credential、session、registration setting | 会话属于唯一账号，可撤销、可过期；注册是否开放由服务器明确控制 |
| 档案与目标 | current profile、measurement、current goal、current strategy | 页面读取当前资料与目标，身体测量形成时间序列；历史计算从各自输入快照读取当时采用值 |
| 训练 | suggestion、routine、routine item、program、program session、program session item、optional schedule、workout session、plan snapshot、actual item | 单次方案可直接训练；周期计划由多周训练单元组成，导入方案时复制内容并保留来源，只有明确安排或选择的内容进入当天训练 |
| 规划计算 | calculation method、evidence reference、daily reference snapshot | 输入、证据、方法版本、输出和警示共同快照 |
| 餐食 | meal、food item、portion、temporary photo、adopted result revision | 盛取量、实际摄入、来源、当前采用值和原图删除状态分开 |
| 模型分析 | task、attempt、raw result、structured candidate | 一个任务可多次尝试，旧候选可与最近失败并存 |
| 运行 | reminder、export、audit event、backup manifest | 不混入产品领域事实，但可审计 |

周期训练单元不保存对单次方案内容的实时引用。它只保留可选的 `source_routine_id`、导入时间和自己的动作副本，用于判断来源是否后来更新并支持用户主动重新导入；核心显示和执行始终读取副本。重新导入采用显式替换而不是自动合并，避免产生难以解释的部分更新。

### 5.3 Migration

- Drizzle schema 用于 TypeScript 查询类型；数据库约束才是最终一致性边界；
- 使用 `drizzle-kit generate` 生成 SQL migration，人工审阅后提交仓库；
- 生产只执行版本化 `migrate`，不使用 `push`；
- 破坏性变更采用“新增结构 → 双读或回填 → 切换 → 后续删除”的前向迁移；
- 每次发布在迁移前创建可恢复备份，并在测试数据库验证迁移和回滚替代方案。

## 6. 规划计算与 AI 估算的隔离

这是本架构最重要的业务边界。

### 6.1 规划计算

系统训练建议和每日营养参考由纯计算模块产生：

```text
当前个人档案 + 相应身体测量 + 当前目标/策略 + 活动/实际训练事实
                    +
        官方证据 ID + 方法版本 + 安全规则
                    ↓
        可复算的建议或每日参考快照
```

- 公式、阈值、适用范围和停止自动计算的条件只来自 `calculation-evidence.md`；
- 每次输出保存输入快照、证据 ID、方法版本、舍入规则、结果和警告；
- 计算模块不读取照片、不调用语言模型，也不根据模型自信度改变目标；
- 同一组测试夹具在相同方法版本下必须得到完全相同的结果；
- 官方建议更新时新增方法版本，不静默回算历史。

因此，“规划准确性”不依赖拍照识别准确性。识别失败只影响这顿饭的记录完整度，不改变系统如何计算每日建议。

### 6.2 图片分析

图片分析只回答“照片里可能有什么、份量和营养大约是多少”。标准流程：

1. API 验证账号、文件大小、允许类型和文件签名，把照片写入临时对象；
2. 数据库事务创建餐食、临时照片元数据和分析任务；临时对象在整个分析与用户复核窗口内保持可读；
3. Worker 领取持久任务，创建一次分析尝试并通过授权存储接口读取临时照片；
4. 视觉提供方返回结果后，服务端保存完整原始响应，并按内部 JSON Schema 校验和归一化；
5. 合法结果形成候选；没有当前采用值时可按产品规则采用，有已有结果时不得静默覆盖；
6. 用户可修改食物、份量和营养值，生成新的采用值修订；
7. 超时、限流和临时错误按退避策略重试；失败时保留餐食和手工补录入口，临时照片只在有效保留窗口内继续用于重试；
8. 写回前再次验证餐食未删除、任务仍有效、照片与任务属于同一账号；
9. 用户确认、修正到满意结果或放弃分析后创建幂等删除任务；原图物理删除失败可重试，但不得删除模型原始结果、采用值或修订历史；
10. 超过临时保留窗口的未确认照片按策略删除，并在餐食与任务上明确记录原图已删除，不能继续承诺复核或重试。

任务创建接受客户端幂等键；Worker 即使重复收到任务也必须产生可识别的尝试，而不能重复创建餐食或覆盖采用值。

### 6.3 模型提供方边界

服务端定义统一的 `VisionAnalysisProvider` 概念，输入是受控图片流、餐次上下文和结构化输出要求，输出包含供应商、模型名、版本标识、原始响应、用量、耗时和候选结构。提供方密钥只存在于服务端 secret。

截至 2026-08-24，DeepSeek 官方“图像理解”指南已经确认 `deepseek-v4-flash-vision-exp` 能通过 OpenAI 兼容 Chat Completions、Responses API 或 Anthropic API 直接接收图片。个人版把它作为首个视觉提供方实现，同时保持适配器边界：

- 首版由服务端从私有临时媒体存储读取单张餐食照片，以 Base64 data URL 发送给 DeepSeek，不创建可公开访问的照片 URL；
- 请求使用 `user` 消息中的文本块和 `image_url` 块；官方支持 JPEG、PNG、GIF、WebP，Base64/外部 URL 单图上限为 32 MiB、请求体上限为 48 MiB，产品自己的上限必须更低；
- 需要复用图片或图片超过内联限制时，才评估 Files API，并另外核对远端文件的保留、删除和隐私规则；
- 初始使用 `original` 细节级别；后续只有在餐食样本验证表明 `low` 不损害所需信息时才用它降低 token 成本；
- 记录提供方、模型 ID、输入方式、细节级别、原始响应、token 用量、耗时和错误；模型仍为实验版本，模型 ID 和适配器必须可替换；
- 即使官方格式允许更大的图片，产品仍设置更保守的上传与解码限制，并在发送前完成文件签名、格式和实际解码校验；
- 真实 API 接入必须通过图片输入、结构化响应、超时、限流、错误分类和隐私边界的契约测试；
- Codex 人工分析保留为结果复核或服务故障补偿，通过受控导入结果进入同一候选与采用流程，不直接改数据库。

普通 `deepseek-v4-flash` / `deepseek-v4-pro` 的纯文本限制不适用于独立的 `deepseek-v4-flash-vision-exp`。官方文档能高置信证明图片输入能力，但不证明模型能准确判断食堂菜品、隐藏油脂、份量和营养；后者继续通过本项目样本验证、范围表达和用户修正控制。

## 7. API 与异步交互

### 7.1 API 形式

- 使用 `/api/v1` 下的 REST JSON API；照片使用受认证的 multipart 上传；
- Fastify JSON Schema 同时约束请求与响应，通过官方 `@fastify/swagger` 生成并提交 OpenAPI 文档；
- 列表使用稳定游标或日期范围，不把全部历史一次返回；
- 写入返回当前 revision 和服务端时间，客户端使用版本条件避免覆盖并发修正；
- 创建餐食、训练记录、照片和任务时支持客户端幂等键；
- 错误响应使用稳定错误代码、可读说明和可恢复动作，不向客户端暴露栈或模型密钥。

### 7.2 异步任务

上传成功后，API 返回 `202 Accepted`、餐食 ID 和任务 ID。Web 默认按退避间隔轮询任务摘要；离开页面不取消任务，重新进入可继续查看。个人版不为这一流程增加 WebSocket。未来若实时事件成为真实需求，可在不改变任务表的前提下加入 SSE。

pg-boss 与业务数据共用 PostgreSQL，使“保存业务记录并安排任务”可以进入同一数据库事务。应用仍按至少一次执行环境设计幂等处理，不依赖供应商对“恰好一次”的宣传作为唯一保障。

- `analysis_task`、`analysis_attempt` 等自有表保存产品可见的权威状态；pg-boss 内部表只负责调度和执行；
- 队列消息只携带可重新校验的任务 ID，不携带照片、密钥、完整模型响应或唯一业务事实；
- Worker 使用 heartbeat 与 expiration 支持异常退出后的恢复，具体时限必须依据真实模型耗时测试；
- 重复领取、模型已响应但结果尚未写回时崩溃、迟到响应和删除后的任务都必须通过条件更新、唯一约束与 revision 保持幂等；
- 实现时固定已通过契约测试的 pg-boss 精确 patch 版本，队列 migration 独立执行，不自动追随当天发布的 latest；
- `TaskQueue` 适配边界只暴露入队、定时、取消待执行任务和注册处理器，避免领域代码依赖 pg-boss 内部表或类型。

## 8. 身份、隐私与安全

### 8.1 账号与会话

- 即使个人版只有一个用户，也提供常规的注册页和登录页，并使用正式账号表和账号归属；系统初始化时预置用户名为 `admin` 的管理员账号，不把首个普通注册用户自动升级为管理员；
- `admin` 不使用硬编码或公开通用密码。部署者通过私密初始化配置提供初始密码，服务端只把 Argon2id 摘要写入数据库，并要求管理员首次登录后更换密码；初始化明文不得进入镜像、仓库或日志；
- 普通账号通过同一注册页自行填写用户名和密码；管理员可以控制是否开放注册，关闭时页面清楚说明当前不接受新账号，不使用邀请码流程；
- `admin` 也可以像普通账号一样使用自己的训练和饮食功能；其额外管理权限与个人健身数据权限分开。首个版本只需要账号启停、注册开关、会话撤销和必要的运行配置；管理员界面默认不提供查看其他用户训练、饮食或临时照片的能力；
- 数据库只保存 Argon2id 标准摘要记录，其中包含算法版本、成本参数、随机盐和不可逆摘要；不得保存密码明文、可逆加密密码或 SHA-256 等快速通用哈希；参数在目标服务器测试后不得低于 OWASP 当前建议；
- 密码原文只允许在注册、登录或重置密码的单次请求内短暂参与校验，不得进入应用日志、错误信息、审计事件、任务载荷、导出或备份清单；忘记密码只能重置，系统不提供找回原密码；
- Web 使用随机、不透明、可撤销的服务端会话；浏览器凭据只放 `HttpOnly`、`SameSite` Cookie，HTTPS 时同时设置 `Secure`；
- 不把 session、JWT、refresh token 或模型密钥写入 `localStorage`；
- 修改密码、主动退出、账号停用和管理员撤销都能结束相关会话；
- Android 的会话传输与安全存储在迁移验证中确认，不能为了复用 Web 而把长期凭据放进普通 Web 存储。

### 8.2 照片与上传

- 只允许明确的图片格式和大小；同时校验扩展名、声明 MIME、实际签名和解码结果；
- 服务端生成对象键，不使用用户文件名作为路径；
- 原图位于 Web 根目录之外，下载必须重新验证账号归属；
- 日志、错误追踪和测试夹具默认不包含原图、密码、会话、模型密钥或完整模型响应；
- 模型请求只发送完成任务所需的照片与最少上下文，记录实际发送的提供方与时间；
- 用户确认、修正到满意结果、放弃分析或删除账号时，均可追踪原图删除状态；删除原图不连带删除已采用的结构化记录。

### 8.3 访问边界

`IP + 端口` 是可行入口，但安全含义取决于网络：

- 同一局域网或受信 VPN 内可以直接以服务器 IP 和端口访问个人实例；
- 只要经过公共互联网并传输密码、照片或健康相关记录，就必须在入口增加 HTTPS；
- 服务端默认只暴露 Web/API 端口，PostgreSQL 和 Worker 不对公网开放；
- 允许来源、代理头和 Cookie 安全属性由部署模式显式配置，不能自动信任任意反向代理。

### 8.4 管理员页面边界

- 管理功能从“设置”进入独立的系统管理路由，不建立第二套前端或新增一级导航；服务端对每个管理 API 单独校验管理员角色，隐藏菜单不能代替权限控制；
- 可管理内容限于注册开放/关闭、账号启停、会话撤销和少量非敏感运行配置；密码重置只生成新的重置过程，不显示现有密码或摘要；
- 可观察内容包括应用版本、数据库与 Worker 健康、pg-boss 任务汇总、视觉提供方是否已配置、临时媒体异常、磁盘余量、最近备份和恢复验证时间；不得显示其他用户照片、模型原始响应或具体健康记录；
- 模型 API key、数据库密码、会话密钥、HTTPS 证书、端口和存储路径仍由部署 secret 或主机配置维护。网页只可显示非敏感的已配置状态，不能读取或复制密钥原文；
- 数据库恢复、全量删除、任意 SQL 和其他高破坏性运维操作不进入管理员页面；管理操作保存操作者、时间、目标、动作和结果，影响其他账号的操作要求二次确认。

## 9. 临时媒体、部署与备份

### 9.1 临时媒体存储

定义统一存储接口：写入临时对象、读取授权流、删除、校验存在性和生成内部对象键。

- 个人版实现为服务器持久目录或 Docker named volume，保证普通重启与容器重建不丢失正在处理的照片；
- 临时媒体位置必须在 Git 工作区之外，与长期业务数据和备份目录分开；
- 数据库保存对象键、大小、哈希、实际 MIME、创建时间和账号归属，不保存原图二进制；
- 用户确认、修正到满意结果或放弃分析后立即进入异步删除；未确认照片超过可配置保留窗口后也进入清理；
- 定时清理没有数据库引用的临时对象，并报告数据库指向但文件缺失、已到期仍未删除或删除失败的异常；
- 当前规模不规划长期图片库、S3 或 MinIO。未来只有明确出现长期保存或多机媒体需求时才新增存储实现。

### 9.2 个人服务器部署

首个部署包使用 Docker Compose，包含：

| 服务 | 责任 | 对外暴露 |
|---|---|---|
| `api` | Fastify API、认证、Vue 静态文件 | 一个配置端口 |
| `worker` | pg-boss 任务、模型调用、提醒、清理、导出 | 不暴露 |
| `postgres` | 业务、会话、任务和审计数据 | 仅内部网络 |

`app` 与 `worker` 使用同一版本镜像；PostgreSQL 和临时照片使用职责分离的持久 volume；模型 key、数据库密码和会话密钥通过 Compose secrets 或等价的主机私密文件注入。反向代理与 TLS 只在需要公网访问时加入部署层，不写进业务应用。

### 9.3 备份与恢复

每个备份批次包含：

1. PostgreSQL `pg_dump` 自定义格式快照；
2. 清单：应用版本、数据库 migration 版本、备份时间、任务与临时照片状态摘要和校验和；
3. 恢复说明和自动校验结果。

临时原图默认不进入长期备份；主机损坏时尚未完成的少量分析可能需要用户重新上传。备份不能只验证“文件生成成功”。发布前和固定周期内要在临时环境执行恢复，核对账号、计划、餐食、图片生命周期元数据、当前采用值和任务状态。备份副本应离开原服务器，并按保留策略加密保存。

## 10. 提醒、历史和导出

- 训练提醒、饮食提醒和身体测量提醒是三类独立规则和任务，不因另一模块异常而互相取消；体重默认每周提醒一次，但周期可调整、暂缓或关闭；
- Web 首先提供应用内提醒，并在用户授权且浏览器支持时使用通知能力；Android 再接本地或推送通知；
- “今天还要练什么”来自当前计划未完成项；“今天还能吃多少”来自系统参考减去当前有效摄入，不额外要求运动热量配额；
- 历史按日期读取该日期当前有效修订与采用值，同时携带当时档案、目标、证据和方法快照；
- 数据导出至少包含机器可读 JSON 和清单，未来可增加 CSV；原始照片不属于长期导出内容。导出与删除均通过后台任务完成并有状态记录。

## 11. 可观测性与测试

### 11.1 运行可见性

- 结构化日志包含 request ID、task ID、模块、耗时和稳定错误代码；明确遮盖 Cookie、Authorization、密码、密钥、照片和模型原始响应；
- `/health/live` 只表示进程存活，`/health/ready` 检查数据库、migration 与任务基础设施；
- 记录任务等待时间、尝试次数、提供方错误类型、过期或未引用临时媒体、删除失败、备份时间和恢复结果；
- 个人版不要求外部监控平台，但日志和健康端点必须能支持排障。

### 11.2 验证层次

| 层次 | 必须验证的内容 |
|---|---|
| 单元测试 | 官方公式、范围、安全停止条件、舍入、日期/时区、计划完成计算 |
| 数据库集成 | 约束、事务、修订、跨账号拒绝、删除与迟到任务、migration |
| 任务集成 | 重试、幂等、旧候选 + 最近失败、提供方超时、Worker 重启 |
| API 合约 | 请求/响应 Schema、权限、并发修正、上传限制、错误代码 |
| 浏览器端到端 | 五个入口、训练闭环、手工记餐、照片等待/失败/修正、历史 |
| 部署验证 | 容器重建后数据仍在、备份恢复、无密钥入镜像或仓库 |
| Android 验证 | 相机、照片上传、会话恢复、网络错误和通知权限 |

模型测试使用经授权、去标识的固定图片集，只评估解析稳定性和产品边界，不把模型估算成绩混作规划公式准确度。

## 12. 开源边界

| 可以进入公开仓库 | 不得进入公开仓库 |
|---|---|
| 源码、migration、测试、部署模板 | 真实账号、密码、会话和 API key |
| 自编且许可明确的少量映射 | 用户照片、餐食、身体档案和训练历史 |
| 官方证据的引用、方法版本和推导说明 | 受限食物数据库或未获授权的动作视频 |
| 脱敏或人工制作的测试夹具 | 生产备份、真实日志和模型原始响应 |

第三方食物库、动作内容和模型供应商都通过接口接入；代码开源不等于可以再分发其数据或媒体。

## 13. 主要取舍

| 选择 | 没有采用的方案 | 原因与代价 |
|---|---|---|
| 模块化单体 | 微服务 | 一人部署和开发成本更低；需要严格模块边界避免变成无结构单体 |
| PostgreSQL + pg-boss | PostgreSQL + Redis 队列 | 少维护一个有状态服务且可事务入队；必须固定 pg-boss 版本并做真实数据库测试 |
| 本地临时媒体存储 | 长期照片库或立即自建 S3/MinIO | 满足分析、重试和用户复核；确认后删除，减少隐私与备份负担 |
| REST + 轮询 | 首版 WebSocket | 已满足异步离页和恢复；短期会产生少量轮询请求 |
| 同源 Web/API | 分离站点和 API 域名 | 简化 Cookie、CORS 和 IP + 端口部署；后续 CDN 化需要调整部署层 |
| Capacitor 首选 | 立即原生重写 | 最大化复用 Vue；必须先验证会话、相机、上传和通知，不把选择当作无条件保证 |

## 15. 进入实现前的验收门

Phase 5 已由产品所有者确认并从增量 0 开始。进入增量 0 时完成：

- 为首个增量建立数据库、上传和跨账号安全测试清单；
- 更新仓库结构说明、AGENTS 阶段约束和根命令；
- 创建 `apps/server/` 和开发部署骨架，`apps/android/` 继续等到 Android 迁移验证时创建。

个人服务器的 CPU 架构、内存、操作系统和访问网络在确定生产 Compose 参数或首次部署前采集；本地工程地基保持可配置，不因尚未连接目标服务器而停工。

进入增量 4 的真实图片分析实现前，再使用实际 DeepSeek API key 完成最小契约验证，覆盖图片输入、结构化输出、用量、超时、限流和错误，并保存测试时采用的模型与官方文档版本。该验证失败只阻塞 DeepSeek 自动分析，不阻塞增量 0–3 的账号、训练、规划和手工饮食能力。
