# Exercise App Phase 3 体验设计

| 项目 | 内容 |
|---|---|
| 阶段 | Phase 3 — 体验设计 |
| 状态 | 已由产品所有者确认，作为 Phase 4 与实现阶段的体验基线 |
| 日期 | 2026-08-24 |
| 上游事实源 | `docs/product.md`、`docs/domain/domain-rules.md` |
| 原型入口 | `apps/web/` |

## 1. 本轮目标

把已经确认的产品能力和领域规则组织成手机上可以连续使用的体验，不实现真实账号、存储、计算、上传或模型调用。

本轮原型验证三件事：

1. 用户打开应用后能否直接看清今天还可以吃多少、还需要练什么；
2. 训练计划与实际完成、系统营养参考与餐食估算能否保持清楚分层；
3. 空白、等待、失败、不完整、修正和安全边界是否都有可继续使用的路径。

## 2. 信息架构

一级导航固定为五个入口：

| 入口 | 用户要完成的任务 | 主要信息 |
|---|---|---|
| 今天 | 判断今天还可以吃多少、还需要练什么并快速记录 | 剩余或超出摄入量、尚未完成的计划项、餐食状态和快捷入口 |
| 训练 | 查看安排并记录真实完成量 | 用户计划、计划项完成情况、额外动作、动作指导入口 |
| 饮食 | 查看建议并记录一餐 | 系统参考、饮食策略、今日已吃与剩余、拍照和食物库入口、分析状态 |
| 历史 | 按日期回顾训练与饮食 | 日期汇总、训练与饮食筛选、修订状态、未知与零值的区别 |
| 设置 | 管理计算输入、提醒和个人数据；管理员进入系统管理 | 首次分步设置、日后按项目修改、身体测量、目标、提醒、导出与删除；仅管理员可见的系统管理入口 |

手机使用底部导航，桌面使用侧栏；两者进入同一信息结构，不产生两套产品。

## 3. 核心流程

### 3.1 首次使用或资料不完整

1. 用户可以先拍照、从食物库记餐或建立自己的训练和饮食计划，不被强制完成整套引导。
2. 第一次进入设置时，页面按“基础资料、身体数据、目标方向、提醒”逐步展示，每一步使用“下一步”，用户也可以暂时离开。
3. 完成后设置首页改为项目目录，用户只进入需要修改的页面，不再同时展开全部表格。
4. 依赖个人资料的系统建议或营养参考明确显示缺少什么，并提供进入设置补充资料的路径；资料不足只停止相关计算，不影响其他模块继续使用。

### 3.2 日常入口

1. 用户进入“今天”。
2. 页面持续展示“还可以吃”与“还要练”：前者由系统参考减去已记录摄入，后者只来自当天已经安排或选择的训练单元；尚未选择的方案库内容不计入当天任务。
3. 用户可以直接进入“拍照记一餐”或“查看训练”。
4. 训练和饮食各自完成记录；餐食变化刷新营养剩余量，训练变化刷新未完成项目，二者互不改写，也不增加联动说明或进食状态询问。

### 3.3 训练

1. 训练页把计划分为“单次方案”和“周期计划”。默认优先展示容易直接开始的单次方案，周期计划作为需要多周编排时进入的独立层级，不要求用户先理解复杂结构。
2. 单次方案可以提前安排到某天，也可以完全不绑定日期。准备训练时，用户可从方案库任选一个，例如练胸时选择“胸 A”或“胸 B”，也可以从空白开始。
3. 周期计划按周和训练日编辑，每周内容可以不同；某个训练单元既可以从空白编辑，也可以从单次方案导入副本。源方案变化时只提示可以重新导入，不自动修改周期内容。
4. 用户重新导入尚未开始的周期训练单元前，页面明确提示这会覆盖该单元的本地调整；进行中或已结束的训练不提供刷新入口。
5. 系统草案、单次方案和周期训练日的动作列表都提供动作预览；选中后形成本次训练，每个动作继续提供完成勾选、实际训练量和动作指导。勾选完成会形成实际记录，不修改来源方案或周期安排。
6. 临时增加的动作作为额外实际记录补充；跳过、替换、少做和多做都保留与本次计划快照的对应关系。
7. 训练进度由已完成实际量和本次剩余动作组成；完成或放弃后以最终实际记录更新当日训练进度。本次计划快照随实际记录保存，之后编辑来源不会改写实际训练，也不会改变当日营养参考。
8. 取消本次训练不产生实际消耗，也不删除可复用方案或周期计划；有其他实际活动时按记录估算，否则保持未知或由用户明确确认没有训练。

### 3.4 每日建议与记餐

1. 页面只使用系统每日营养参考作为数值比较基准，不提供用户手填数值目标；用户选择有官方依据的目标策略和范围内偏好，由系统计算建议。
2. 页面同时展示系统建议、已记录摄入和剩余或超出量；记录不完整时明确说明只基于已记录内容。
3. “拍照记一餐”和“添加食物”是同级入口。添加食物支持从个人常用食物快速加入、从最近一餐中勾选部分食物复用，以及搜索食物、菜品或包装食品；加入后可以按当天实际份量调整，没有合适条目时允许手工补充。
4. 用户拍照或选择照片后，照片先被可靠暂存并关联到餐食；说明和营养明细都可以稍后补充。自动分析开启时创建分析任务，关闭时保留手工发起入口。
5. 没有当前采用值时，成功结果成为明确标记的暂定采用值；用户可以确认、修正或拒绝，已有确认值不会被重新分析自动覆盖。
6. 用户确认、修正到满意结果或放弃分析后，界面说明原图将被删除；结构化餐食和修订历史继续存在。
7. 用户饮食计划仍可作为可选的餐次或食物安排，但不覆盖系统每日营养参考，也不占据饮食主页的主要层级。

### 3.5 历史

1. 当前采用按日期组织的统一历史：每个日期内分别展示训练和饮食摘要。
2. 页面提供“全部、训练、饮食”筛选；默认显示全部，用户不需要先选择模块才能回看某一天。
3. 日期是当前主索引，筛选是辅助视图。这一结构不提前锁死未来是否增加独立训练趋势或饮食趋势页面。
4. 训练历史默认展示当日实际完成的动作、组次、重量、次数、时长和额外动作，不提供计划版本浏览；计划项关系只在需要解释跳过、替换或计划来源时进入详情。

### 3.6 实际训练与原计划不同

1. 不预设训练发生在晚上；早上、白天或晚上都使用同一套训练记录流程。
2. 实际训练只更新完成情况、训练量、消耗估算和历史，不改写当天营养参考。
3. “还可以吃”始终用系统参考减去当前已记录摄入；尚未记餐时显示完整参考，超出时显示超出量，并注明记录完整性。
4. “还要练”随计划项完成勾选减少，额外训练另行记录，不把训练表达成热量配额。

### 3.7 管理员进入系统管理

1. `admin` 从“设置”进入仅管理员可见的“系统管理”，不增加第六个一级入口；普通用户不显示入口，直接访问管理 URL 时返回无权限状态。
2. 管理区分为注册与账号、服务状态、系统配置三组；首版只提供注册开关、账号启停、会话撤销和必要的非敏感运行配置。
3. 服务状态只显示应用、数据库、Worker、模型配置状态、任务汇总、临时媒体异常、磁盘和备份摘要，不展示其他用户的照片、模型原始响应或具体健康记录。
4. 密钥、数据库密码、会话密钥、HTTPS 证书、端口、存储路径、恢复数据库和任意 SQL 不进入网页管理界面。
5. 管理操作记录操作者、时间、目标和结果；停用账号、撤销其他账号会话等影响性操作需要明确确认。

### 3.8 更新档案与身体测量

1. 首次设置使用可随时离开的分步流程；完成后设置首页只展示基础资料、身体测量、目标与营养、提醒、数据与账号等入口。记录体重或腰围是新增一条带时间的测量，不是覆盖旧值。
2. 当前体重旁显示采用值和测量日期，并提供趋势入口；新增有效体重后，当天及后续参考使用新值，过去日期保持原样。
3. 体重默认每周柔性提醒一次，用户可以改变周期、暂缓或关闭。未更新时只提示当前仍采用哪一天的记录，不显示失败、惩罚或必须补全状态。
4. 身体测量提醒与训练提醒、饮食提醒分开设置；身高等稳定档案信息只在用户知道发生变化时编辑，不设置统一强制复核周期。
5. Bug 反馈使用独立页面，不与资料、提醒或账号表格混排。用户可以先填写现象，再生成包含当前页面、浏览器环境、服务健康状态和近期接口/页面错误的文本；报告可以预览、复制或下载，系统不自动上传，也不采集凭证、照片或训练饮食明细。

## 4. 信息分层

界面必须持续保持以下分离：

- 训练建议来源、用户训练计划、与计划项关联的实际记录及额外实际记录；
- 用户饮食计划、饮食策略输入和系统每日营养参考；
- 餐食记录、模型原始估算、当前采用值；
- 规划目标、已记录摄入、剩余量或偏差；
- 当前个人档案、身体测量时间序列、计算时采用的输入快照；
- 已保存记录的处理完整性、全天摄入覆盖状态。

界面不得只用颜色表达这些差别，每个状态同时使用文字名称和解释。

## 5. 状态体验

| 状态 | 页面表达 | 继续路径 |
|---|---|---|
| 正常 | 展示系统参考、记录和来源 | 继续记录或查看详情 |
| 空白 | 说明当前没有什么以及为什么有用 | 提供一个明确的开始动作 |
| 等待 | 明确照片已可靠暂存、分析尚未完成 | 允许离开页面，稍后返回 |
| 失败 | 说明哪一次分析失败、餐食仍存在，以及临时照片是否仍可重试 | 重试、手工录入、放弃并删除原图或暂不处理 |
| 不完整 | 只汇总已知值并说明覆盖未知 | 继续使用，不强制补录 |
| 测量较旧 | 显示当前采用的体重及测量日期，不把“没有新记录”表述成体重未变化 | 立即记录、暂缓提醒或继续使用 |
| 修正 | 新修订成为当前值，旧结果仍可追溯 | 保存修订或返回候选 |
| 安全边界 | 停止输出不适用的个性化数值 | 补充必要资料、手工设定或只记录 |

## 6. 界面文案

- 页面写给正在使用产品的人，不写给评审者；优先使用“你”“我的”和具体动作。
- “系统每日营养参考”“饮食策略”“当前采用值”等领域名词继续保留在规则和数据设计中，界面只在用户确实需要分辨来源时显示。
- 按钮直接说明按下后要做什么，例如“补全资料”“自己填写”“再试一次”。
- 缺失、不完整和失败状态只说明发生了什么、数据是否还在以及接下来能做什么，不反复解释系统设计原则。
- 标题不使用口号、对仗句或需求文档式总结。

## 7. 原型交互边界

- 当前可点击导航、计划项完成、今日剩余训练同步、额外动作、饮食记录入口、历史筛选、提醒开关和图片分析状态演示；个人资料、动作指导和计划编辑只表达后续流程入口。
- 所有营养值使用“—”表示等待真实个人资料和正式计算，不制造示例目标。
- “上传成功”“分析返回”和“保存修订”仅切换低保真演示状态，不读取照片、不调用模型、不保存数据。
- 当前不加入 Router、状态库、数据库、服务端、图片上传、通知权限或模型配置。
- Phase 3 低保真原型当时未补做管理员页面；Phase 5 增量 0 已按本节边界在“设置”下增加独立管理员路由，仍保持五个一级入口。

## 8. 整体纠正重点

产品所有者已整体认可当前版本；以下项目继续作为实现阶段的回归检查：

1. 五个一级入口是否符合日常使用习惯；
2. “今天”是否把最重要的判断和快捷入口放在首屏；
3. 训练计划与完成记录的组合、系统饮食建议与已吃/剩余的关系是否自然；
4. 图片等待、暂定、失败和修正是否符合预期；
5. 按日期汇总并提供训练/饮食筛选的历史结构是否适合作为当前默认；
6. “还可以吃”与“还要练”是否能持续提供明确结果，且不会混淆训练提醒和饮食提醒。
