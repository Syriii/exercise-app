| D-014 | 个人阶段把可由应用调用的多模态 API 作为图片分析主要执行方式，Codex 保留为不可用、复核和特殊情况的人工补偿 | 产品所有者确认已具备多模态 API 能力，图片分析不必继续依赖人工启动 Codex | 实际 API 无法满足图片输入、稳定性、费用、隐私或估算质量要求 |
| D-015 | 配置并授权多模态服务后默认自动分析新照片；没有既有采用值时，模型结果自动成为计入统计的暂定采用值，但不得覆盖手工或已确认结果 | 减少日常拍照后的额外确认负担，同时保留估算状态、用户修正权和结果可追溯性 | 实际使用表明自动发送、费用、误识别或暂定值参与统计造成不可接受的风险或干扰 |
| D-016 | 系统每日能量与营养目标作为独立规划基准，准确性优先于餐食图片识别准确性和实现便利；识别不确定性只影响实际摄入及偏差判断 | 产品所有者明确要求系统提供的计划与每日阈值准确，不能因多模态识别属于估算而降低规划计算质量 | 产品所有者改变规划基准与实际摄入估算的责任边界 |
| D-017 | 接受“周能量预算 + 训练净消耗相对周均值日分配 + 宏量营养约束”的规划结构；所有公式、阈值、适用范围和安全边界必须有可定位的官方文档背书，产品推导必须公开依据和过程 | 产品所有者认可高准确性营养规划方案 v2，并明确要求所有相关信息具有官方文档依据 | 官方依据更新、适用人群改变或验证发现当前推导不成立 |
| D-018 | `docs/domain/domain-rules.md` 作为当前领域事实源获得整体确认，Phase 2 结束并进入体验设计阶段 | 产品所有者审阅规则说明后确认整体没有问题；领域稿已覆盖关键输入、结果、不确定性、修正和异常路径 | 产品所有者明确改变使用方式，或证据更新导致领域规则需要修订 |
| D-019 | Web 前端采用 Vue 3 + TypeScript + Vite，现有 React 展示骨架立即迁移；路由、状态管理和其他库仍按真实需求决定 | 产品所有者明确选择 Vue；当前尚无业务组件，迁移成本低，且 Vue 官方支持 Vite 与 TypeScript，后续 Web 容器 Android 路线不受影响 | Vue 无法满足已确认体验、维护或 Android 演进要求 |
| D-021 | 训练主页只呈现用户计划与实际完成：系统建议只作为建立计划的候选，采用或编辑后成为用户计划；实际记录由计划项完成情况与额外动作共同组成 | 产品所有者明确说明系统建议和我的计划最终应整合，训练时应以计划打勾并补充额外内容 | 实际使用证明需要在训练主页长期并列多份安排，或完成记录无法与计划项关联 |
| D-022 | 饮食页只使用有官方依据的系统每日营养参考作为数值基准，不提供用户手填营养目标；用户选择目标策略和官方范围内偏好，拍照与食物库搜索作为同级记餐入口 | 产品所有者要求规划准确性优先，并明确不需要个人另设数值目标，希望兼顾食堂拍照和类似薄荷健康的手动搜选食物方式 | 产品所有者重新要求自定义数值目标，或官方依据无法支持现有策略选项 |
| D-023 | 历史当前默认按日期汇总，每日内分别展示训练与饮食，并提供“全部、训练、饮食”筛选 | 产品所有者尚未决定是否永久拆分训练与饮食历史；日期主索引兼容两种查看方式且容易调整 | 实际使用显示用户主要按单一模块连续回顾，日期结构妨碍核心任务 |
| D-024 | 训练可发生在任意时段；“今天”持续展示系统参考减去已记录摄入后的剩余或超出量，以及计划中尚未完成的训练内容，不再询问是否还会继续进食或设置单独联动区块 | 产品所有者认为日常需要的是持续可见的两个结果，而不是解释实际训练如何影响饮食或要求补充进食状态 | 实际使用表明这两个结果不足以支持当日决策，或产品所有者重新要求显式展示联动过程 |
| D-025 | 当前移动端优先的五入口体验、训练与饮食页面模型、日期主索引历史和状态边界作为 Phase 3 基线，项目进入技术与版本规划 | 产品所有者确认当前版本整体不错；体验稿已覆盖已确认产品和领域规则，并经过响应式与交互复核 | Phase 4 发现当前体验无法可靠实现，或真实个人使用暴露核心流程问题 |
| D-026 | 餐食原图只在分析、重试和用户复核期间可靠暂存；用户确认或修正到满意结果、或放弃该次分析后异步删除原图，长期保留结构化估算、采用值和修订历史 | 原图的价值在于辅助得到可信的结构化记录，确认后继续保存会增加隐私、存储和备份负担 | 用户明确需要照片历史、模型复核必须依赖原图，或删除妨碍已确认的核心流程 |
| D-027 | 个人版和朋友版的后台任务采用 pg-boss，由 PostgreSQL 同时承载业务数据与队列；自有任务和尝试记录保持权威，系统按至少一次执行设计，当前不引入 Redis | 当前规模不超过十人，pg-boss 能事务内入队，并以开源版 heartbeat 与 expiration 支持异常 Worker 恢复；相比 Redis 队列少维护一个有状态服务 | 本地故障测试无法达到恢复要求、任务规模或隔离需求显著增长，或依赖维护状态发生不可接受的变化 |
| D-028 | 密码不得以明文或可逆形式进入数据库及其他持久记录；数据库只保存按当前安全基线生成的 Argon2id 摘要，忘记密码只能重置 | 产品所有者明确要求数据库不得明文保存密码；不可逆、带独立盐且成本可调的密码摘要能降低数据库泄露后的风险 | 适用安全标准或官方建议更新，需要迁移到更合适的密码摘要算法 |
| D-030 | 账号采用常规注册页和登录页，不使用邀请码；系统预置 `admin` 管理员账号并由私密部署配置设置初始密码，普通注册用户不会自动成为管理员 | 产品所有者希望保留正常登录注册，同时明确需要默认管理员承担少量管理和配置职责；分离管理员与普通注册避免首用户抢占权限 | 产品改用外部身份系统、取消应用管理员，或管理职责显著扩大 |
| D-031 | 管理员功能作为“设置”下仅 `admin` 可见的系统管理区，不增加一级导航；首版只管理账号、注册、会话、非敏感配置和运行状态，不提供查看他人健康数据、读取密钥或执行高风险数据库操作 | 当前管理需求很少，独立复杂后台会增加不必要的页面和权限面；管理员仍需要完成基本配置与排障 | 管理任务显著增加、需要独立运维人员，或合规要求必须建立专用管理应用 |
| D-034 | 训练计划采用“单次训练方案 + 周期训练计划”双层模型：简单用户直接使用可复用单次方案，复杂用户按多周和训练日自由编排；周期训练单元导入单次方案时保存副本，不实时联动，只允许用户主动重新导入刷新尚未开始的单元 | 产品所有者需要同时支持临场任选练胸等单次方案和每周内容不同的高度自定义复杂计划，并认为实时引用不便于控制 | 实际使用证明双层入口仍过于复杂、需要实时联动，或周期计划需要更高级的自动编排规则 |
| D-035 | 个人资料采用“当前档案/目标/策略 + 身体测量时间序列 + 每次计算输入快照”，不提供通用档案或目标版本浏览；历史建议、每日参考和消耗估算从各自快照解释当时依据 | 产品所有者确认当前资料、身体趋势和每日计算依据已经满足使用需要，通用版本管理会增加不必要复杂度 | 真实使用需要恢复旧档案、安排未来多套目标，或现有快照不足以支持历史修正 |
| D-036 | 体重按测量时间连续保存，默认提供每周一次且可调整、暂缓或关闭的柔性提醒；未更新不阻断使用，当前计算继续采用最近一次有效体重并显示测量日期，新增体重只影响当天及以后 | 国家卫生健康委要求定期监测体重和腰围，CDC 官方材料把每周记录体重列为体重管理监测方式；产品所有者确认提醒不得成为强制打卡 | 官方依据更新、特殊人群需要不同监测方式，或实际使用表明默认周期造成明显干扰 |
| D-037 | 采用 `technical-architecture.md` 的模块化单体技术架构与 `delivery-plan.md` 的八个可运行增量顺序，Phase 4 结束并从 Phase 5 增量 0“工程与数据地基”开始实现 | 产品所有者在完整架构、风险门与交付顺序汇总后要求继续；此前各项关键组件和业务边界均已逐项确认 | 增量 0 的本地验证证明核心组合不可运行，或产品所有者明确调整整体技术方向与交付顺序 |
