## 1. 产品定位

Exercise App 是一款移动优先的个人健身辅助产品，由相互独立但共享必要数据的训练模块和饮食模块组成。

- 训练模块帮助用户规划怎么练、获得动作指导，并记录实际练了多少。
- 饮食模块帮助用户制定饮食安排、获得每日营养参考，并估算和记录实际吃了多少。
- “今天”并列展示饮食剩余量与训练完成进度；单日实际训练不改写当天饮食参考。

产品首先服务项目所有者本人。个人使用效果满意后，开放给朋友使用；Web 体验满意后，提供 Android APK。项目通过公开 GitHub 仓库开源。

## 2. 核心问题与价值

健身需要同时处理训练和饮食，但两件事有各自独立的决策和记录过程。当前最突出的现实困难来自饮食：用户主要在食堂就餐，通常无法获得菜品的准确配方、重量、用油和营养标签，手动计算每餐摄入的成本很高。

产品要形成两个可以分别使用的闭环：

1. **训练闭环：** 获得建议或自主安排训练 → 查看当天计划与动作指导 → 录入实际完成内容 → 回顾训练量和消耗参考。
2. **饮食闭环：** 获得每日目标与饮食安排 → 拍照或手动记录一餐 → 获得可修正的营养估算 → 查看当天已摄入、剩余或超出。

训练与饮食在“今天”和历史中并列呈现，但各自保持独立计算和记录，不要求用户必须同时使用两边。

## 3. 用户与产品演进范围

### 3.1 使用人群

- **个人阶段：** 项目所有者在自己的长期运行服务器上日常使用。
- **朋友阶段：** 朋友在同一套服务器中拥有各自的独立账号。
- **开源阶段：** MIT License 允许其他人使用、修改和自行部署项目。

开放给朋友后，每位用户拥有独立的个人档案、训练记录、饮食记录和临时餐食照片处理空间，默认只能访问自己的数据。

### 3.2 交付形态

- 第一交付形态是适合手机使用的 Web 应用。
- Web 体验达到产品所有者认可后，产品继续形成可安装的 Android APK；具体 Android 技术路径后续确定。
- 视觉方向为运动、简洁、实用，优先满足手机上的快速查看和记录。
- 面向其他人的完整部署说明、配置示例和初始化流程在产品稳定完成后提供；需求频繁变化的个人测试阶段不承担这项交付。

## 4. 产品原则

### 4.1 已确认原则

1. **模块独立，并列呈现。** 训练与饮食可以分别使用；“还能吃多少”和“还需练多少”同时展示，但互不改写。
2. **用户拥有决定权。** 系统提供建议，用户可以采用、修改或完全忽略；产品不强制用户按建议训练或饮食。
3. **使用频率由用户决定。** 不强制打卡，不设必须完成的记录配额；少记录或漏记不会阻断其他功能。
4. **计划与事实分开。** 训练建议、用户训练计划和实际训练记录具有不同含义，不能相互覆盖。
5. **记录可以稍后完成。** 图片暂时无法分析时仍可保存餐食并在短期保留原图以便重试；没有照片或不愿补录时也不影响程序继续使用。
6. **提醒职责分开。** 训练提醒只表达训练相关事项，饮食提醒只表达摄入目标与偏差。
7. **历史事实不被后来状态改写。** 体重或目标变化只影响当天及之后的参考，不重新计算过去的训练、饮食和当时目标。
8. **规划准确性优先。** 系统生成每日能量和营养目标时，应优先采用可信、适用且经过核对的官方依据与计算方法；每个公式、阈值、适用范围和安全边界都必须能够追溯到具体官方文档及版本。不能因为实际摄入需要通过图片估算，就降低目标与阈值本身的准确性要求。
9. **规划与摄入估算分层。** 每日目标是系统规划基准，照片分析是对实际摄入的估算；识别结果的不确定性影响“吃了多少”和据此计算的剩余或偏差，不反向改变系统目标的计算质量。
10. **估算不冒充测量。** 即使规划计算采用可靠依据，个人真实需要、运动消耗和图片识别结果仍不能冒充直接测量或医疗处方。

### 4.2 由已确认方向导出的原则

以下原则是为保持产品可信和可持续使用而作出的产品推导，需在后续领域规则与体验设计中验证：

- 估算应表达不确定性，避免用不合理的精确度制造确定感。
- 用户应能看到必要的估算依据，并修正明显错误。
- 健身和营养建议属于一般性辅助，不替代医疗诊断或专业治疗建议。
- 数据越完整，反馈通常越有参考价值；但产品只说明数据缺失的影响，不评价或惩罚用户。

## 5. 产品能力地图

### 5.1 训练模块

#### 训练建议与计划

- 系统可以根据用户当前身体情况和健身目标提出训练建议。
- 系统建议是建立计划时可用的起点，不是训练页上与用户计划长期并列的一套安排。
- 用户的计划能力分为两层：单次训练方案保存一次训练的可复用动作组合；周期训练计划按周和训练日组合多个训练单元，并允许每周内容不同。
- 用户可以直接采用或编辑系统建议，使其成为单次方案或周期计划中的训练单元；也可以放弃建议，从空白创建。单次方案可以同时保存多个，例如不同练胸方案、不同器械环境或不同时长的安排。
- 单次方案不必绑定每周固定日期。用户可以到准备训练时任选一个、提前安排到某天，或不使用方案直接记录。周期计划用于需要多周结构和高度自定义安排的场景，但不强迫所有用户使用。
- 周期计划把单次方案导入某个训练单元时保存独立副本，不与源方案实时联动。源方案更新后，用户可以主动重新导入来刷新尚未开始的训练单元；刷新前说明会覆盖该单元的本地修改。
- 用户可以查看当天已经明确安排或选择的训练及具体动作；尚未选择的方案库和周期计划其他训练单元不计入“今天还要练”。

#### 动作指导

- 用户可以查看用于理解标准姿势的动作示范视频，并获得动作要点或同等指导内容。
- 动作指导在查看系统草案、单次方案、周期训练日和实际训练时都可进入，不要求用户先开始训练。
- 指导内容的来源、质量标准和责任边界在后续阶段确定。

#### 实际训练记录

- 用户在训练时以当天已安排或临时选中的方案为起点逐项标记完成、跳过或替换，并记录实际训练量；也可以从空白开始。
- 用户可以在计划之外补充临时增加的动作或活动。
- 实际完成内容不自动改写原训练计划。
- 产品结合个人体重等个人情况和实际训练内容，对运动消耗作近似估算。

#### 训练回顾与提醒

- 用户可以回顾历史训练和变化趋势。
- 产品提供独立的训练提醒，用户可以自行决定是否开启以及提醒时间。

训练模块可以单独使用，不要求用户同时记录饮食。

### 5.2 饮食模块

#### 饮食计划与每日建议

- 用户可以制定自己的饮食计划。
- 产品根据个人情况、健身目标、用户选择的饮食策略和当天活动情况，给出每日热量、蛋白质、脂肪等营养参考。
- 系统每日营养参考是饮食页唯一的数值比较基准，用户不另外手填一套营养目标。
- 用户选择的是有适用官方依据的目标策略或范围内偏好，例如在健康规律训练且适用时选择偏高蛋白，或在减脂策略中选择官方脂肪范围内较低的分配；选项不能突破适用范围，也不能成为没有依据的隐藏数值。
- 每日营养参考独立于餐食识别质量：系统应使用适用、可追溯且经过核对的官方依据，优先保证公式、阈值和边界的实现正确；没有官方依据支持的数值不能进入自动规划核心。
- 饮食计划仍是用户可选的餐次或食物安排，但不覆盖系统每日营养参考。

#### 餐食记录

- 拍照是食堂等难以获得准确配方场景下的主要记录入口。
- 上传照片时，用户可以选择性补充简短文字，例如份量、隐藏食材或实际食用比例；说明不是保存和分析的必填项。
- 用户也可以从食物库中搜索食物、菜品或包装食品，选择实际份量后加入这一餐；没有合适条目时仍可手动录入。
- 用户也可以什么都不补录；未记录的一餐不会生成强制任务，也不会阻断训练或其他饮食功能。
- 用户可以把确认过的单个食物保存为个人常用食物，以后快速加入某一餐并按当天实际情况调整份量。
- 用户也可以查看最近实际记录过的餐食，只选择其中仍然相同的部分加入今天的餐食，再补充当天不同的内容；例如从昨天早餐复用鸡蛋和豆浆，但不复制昨天的包子。

#### 图片营养估算

- 产品支持根据餐食照片估算食物、份量、热量和营养成分。
- 图片分析结果允许用户接受或修正。
- 模型原始估算与当前采用值都要保留。当前采用值是当前计入统计的有效结果，并区分未经确认的暂定值与用户确认或修正后的确认值。
- 如果餐食还没有当前采用值，图片分析结果自动成为暂定采用值并计入统计；如果已经存在手工值或确认值，新模型结果不得自动覆盖。
- 结果发生修正后，该餐和对应日期的汇总随之更新。
- 当图片分析暂时不可用或失败时，餐食记录继续存在，原照片在临时保留期内可用于稍后分析或重试。
- 图片只作为临时分析材料；用户确认、修正到满意结果或放弃本次分析后，服务端异步删除原图，结构化结果与修订历史继续保留。

#### 当天反馈、回顾与提醒

- 产品累计当天已有餐食记录的营养估算。
- 产品以“系统每日营养参考 − 当前已记录摄入”展示还可以摄入多少；超过参考时展示超出量，并在记录不完整时说明结果只基于已有数据。
- 当天尚未记录任何餐食时，当前已记录摄入为 0，页面展示完整的系统每日营养参考作为剩余量，同时明确标记“尚未记餐”；已有餐食中的未知营养值不按 0 处理。
- 图片识别的不确定性只降低已摄入、剩余量和偏差判断的置信程度，不改变系统每日营养目标本身。
- 用户可以回顾历史饮食和营养变化趋势。
- 产品提供独立的饮食提醒，用户可以自行决定是否开启以及提醒时间。

饮食模块可以单独使用，不要求用户当天必须训练。

### 5.3 训练与饮食并列展示

- 用户可以在早上、白天或晚上训练。计划时间由用户安排，实际时间由训练记录产生；产品不能默认训练发生在晚上。
- “今天”持续展示两项独立结果：系统每日营养参考减去已记录摄入后的剩余或超出量，以及用户计划中尚未完成的训练内容。
- 系统每日营养参考使用个人档案、体重策略、饮食策略和已经确认的惯常活动水平生成；某一天实际多练、少练、取消或补做，不自动改变当天可以吃多少。
- 训练完成情况只减少尚未完成的计划项，不形成需要通过运动“挣取”的热量，也不要求用户完成消耗配额。
- 训练提醒和饮食提醒仍各自独立；训练记录、运动消耗估算和饮食汇总可以在历史中并列查看，但不互相改写。

### 5.4 通用基础能力

- **个人档案：** 保存并更新生成训练和营养参考所需的个人信息与目标。
- **身体测量：** 体重、腰围等按测量时间连续保存，新增记录不覆盖旧记录；最新有效记录用于当前计算并明确显示测量日期。
- **档案更新提醒：** 体重默认提供每周一次的可选提醒，用户可以调整、暂缓或关闭；未按时更新不阻断使用，系统继续采用最近一次有效记录并说明其日期。
- **时间有效性：** 体重或目标更新只影响当天及之后；历史记录保留当时采用的信息和结果。
- **历史回顾：** 查看过去的训练、饮食及其变化趋势。
- **记录修正：** 修改错误或不完整的训练、饮食和估算结果。
- **数据控制：** 查看、导出、备份或删除自己的长期记录。
- **数据持久性：** 应用更新、重新部署或重启后，业务记录和仍在处理期内的临时照片不应意外丢失；已经确认的结构化结果不依赖原图继续存在。
- **账号与数据隔离：** 多用户阶段每个账号拥有独立数据空间，默认不能访问他人数据。
- **提醒设置：** 用户自行决定提醒是否开启及其时间。
- **Bug 反馈：** 使用独立页面生成、检查、复制或下载用于排障的问题报告，不与资料、提醒或账号设置混排；报告不得自动上传，自动收集部分不得包含密码、会话、API Key、照片、请求内容或训练饮食明细。
- **设置流程：** 第一次设置使用可跳过的分步引导；完成后按基础资料、身体测量、目标与营养、提醒、数据与账号分别进入修改，不把全部表格同时展开。
- **不完整数据处理：** 数据不完整时应用继续可用，同时说明相关统计或建议可能受到的影响。
- **跨日状态：** 清楚区分当天计划、当天实际记录和历史结果。

以上能力均为产品必备基础，不再作为“是否需要”的开放问题。

## 6. 核心使用场景

### 6.1 自主规划并记录训练

用户可以建立单次训练方案，也可以把多个训练单元组合成每周内容可不同的周期训练计划。单次方案可以绑定某天，也可以只按训练目的保存并在训练开始时任选一个，例如在练胸当天选择“胸 A”或“胸 B”；复杂用户可以在周期计划中安排第 1 周胸 A、第 2 周胸 B。周期训练单元从单次方案导入时取得副本，只有用户主动重新导入才刷新。训练过程中围绕本次选中的内容和实际完成情况工作：动作逐项勾选并填写实际完成量，临时增加的动作作为额外记录补充。历史回顾以长期保存的实际训练为主；本次训练需要的计划上下文随实际记录保存。

### 6.2 在食堂拍照记录一餐

用户拍摄或选择餐食照片，必要时补充一句说明。照片被可靠暂存并关联到餐食；分析完成后，用户查看并按需要修正估算，当前采用值计入当天汇总。用户确认或修正到满意结果后，原图进入异步删除流程，餐食数据继续保留。

### 6.3 不拍照或无法分析时继续记录

用户可以搜索食物库中的食物、菜品或包装食品，也可以从个人常用食物快速加入、从最近一餐中只选择部分食物复用，或直接手动录入。复用结果是当前餐食的独立快照，可以继续按当天份量调整；如果用户不想补录，应用保留已有数据并继续工作，不制造必须清空的任务或使用障碍。

### 6.4 实际训练与原计划不同

无论训练发生在早上、白天还是晚上，实际训练只更新本次训练的完成情况、训练量和历史事实，不改变当天营养参考。“今天”始终独立显示还可以吃多少或已经超出多少，以及按计划完成情况还需要练什么。训练提醒和饮食提醒各自保持独立。

### 6.5 个人状态或目标变化

用户记录新的体重或更新健身目标后，新的状态用于当天及后续建议；过去的训练、饮食和当时参考保持原样，以便历史回顾能够反映当时真实情况。体重记录是可回顾的测量时间序列，不是反复覆盖同一个档案字段；用户没有按建议周期更新时，应用继续使用最近一次有效体重并标明测量日期，不强制补录。

## 7. 个人阶段运行模式与约束

### 7.1 长期运行与手机访问

- 为支持日常手机拍照，Web 应用部署在产品所有者可控、能够长期运行并可由手机访问的服务器上。
- 个人阶段允许通过服务器 IP 和端口访问，不以拥有域名作为使用前提。
- 外网暴露、连接加密和访问安全采用什么方案，属于技术规划问题；产品层要求个人数据不能因访问方式而失去必要保护。

### 7.2 源码与运行数据

- 公开 GitHub 仓库保存可以公开的源代码、文档和部署配置。
- 临时餐食照片、个人档案、训练记录、饮食记录和访问凭证属于私有运行数据，不进入公开仓库。
- 照片只在部署服务器上可靠暂存到分析、重试和用户复核完成；确认、修正到满意结果或放弃分析后异步删除，不作为长期照片库。
- 代码更新、应用重启或重新部署不能导致业务记录或仍在有效处理期内的临时照片意外丢失；删除原图后，已经采用的结构化结果必须继续存在。
- 产品需要具备长期业务数据的访问控制、备份和恢复能力；临时照片默认不进入长期备份，具体保留窗口和失败清理策略在技术规划中确定。

### 7.3 当前图片分析方式

产品所有者现在已经具备可供应用调用的多模态模型 API，图片分析不再只能依赖事后人工启动 Codex。个人阶段仍采用异步、可替换的分析方式：

1. 手机先把照片上传到长期运行服务器的临时存储，形成待分析餐食记录。
2. 用户完成多模态服务配置和照片发送授权后，自动分析默认开启，应用在照片保存成功后创建分析任务；用户可以关闭并改为手动发起。
3. 服务端把该任务明确授权的照片和可选说明发送给已配置的多模态分析服务，取得结构化候选估算并回填原记录。
4. 餐食没有当前采用值时，候选结果自动成为计入统计的暂定采用值；用户可以确认、修正或拒绝，已有手工值或确认值不会被新结果自动覆盖。
5. 获取、分析或回填失败时，原记录保留，临时照片在有效保留期内可重试，不影响其他功能。
6. 用户确认、修正到满意结果或放弃本次分析后，服务端异步删除原图；模型原始估算、当前采用值和修订记录按长期业务数据保留。

多模态 API 是当前主要分析执行方式；Codex 保留为服务不可用、结果复核或特殊餐食处理时的人工补偿方式。未来仍可以更换其他云端模型、本地模型或图片分析执行者，但临时照片生命周期、分析任务、模型原始估算、当前采用值、修正和汇总的产品关系保持不变。

用户需要知道照片是否会发送给外部服务，并能控制是否启用自动分析。具体供应商、模型、接口、凭证、费用、失败策略和数据处理方式在技术规划阶段确定。

## 8. 边界与后续阶段
